# SessionFlow — документация для разработки

Как устроена система. Что входит в первую версию — в [mvp.md](mvp.md).

## 1. Основные сущности

### Session

Представляет отдельную сессию Claude Code.

Поля:

- Уникальный идентификатор сессии.
- Название задачи.
- Путь к проекту.
- Время создания и последней активности.
- Текущий статус.
- Последняя известная операция.
- Краткое описание прогресса.
- Последнее сообщение или событие.
- Список изменённых файлов, если эти данные доступны.
- Ссылка на исходную сессию или возможность открыть её средствами Claude Code.

### Task

Представляет логическую задачу, которую нужно выполнить.

Поля:

- Идентификатор.
- Название и описание.
- Статус Kanban.
- Связанные сессии.
- Приоритет.
- Дата создания и обновления.
- Результат выполнения.

Одна задача потенциально может включать несколько сессий.

### Project

Представляет локальный проект или Git-репозиторий.

Поля:

- Название.
- Путь к директории.
- Git-репозиторий, если доступен.
- Связанные сессии и задачи.

## 2. Kanban-доска

Основной интерфейс состоит из колонок:

1. **Inbox** — новые или ещё не классифицированные сессии.
2. **Todo** — задачи, которые предстоит выполнить.
3. **In Progress** — активная работа.
4. **Waiting** — сессии, ожидающие ответа, подтверждения или другого внешнего действия.
5. **Review** — работа завершена или готова к проверке человеком.
6. **Done** — подтверждённо завершённые задачи.

Статус сессии и статус задачи должны храниться отдельно.

Например, задача может находиться в колонке Review, хотя породившая её сессия Claude Code уже завершилась. Перемещение карточки пользователем не должно подменять фактическое состояние процесса.

Карточка должна показывать:

- Название задачи.
- Проект.
- Статус сессии.
- Время последней активности.
- Краткий прогресс.
- Наличие ошибок или ожидающих действий.

Пользователь должен иметь возможность открывать подробности карточки, фильтровать задачи по проектам и вручную перемещать их между колонками.

## 3. Мониторинг сессий

Приложение должно находить локальные сессии Claude Code и получать доступную информацию об их состоянии.

Источники данных:

- Локальные файлы истории сессий.
- События и хуки Claude Code, если они доступны.
- Сведения о работающих процессах, если это необходимо.
- Git и файловая система для дополнительного контекста.

Мониторинг должен поддерживать:

- Первоначальное сканирование существующих сессий.
- Обнаружение новых сессий.
- Отслеживание изменений.
- Обработку неполных или повреждённых записей.
- Исключение повторной обработки одних и тех же событий.
- Восстановление после перезапуска SessionFlow.

Приложение должно работать локально и не зависеть от постоянного доступа к облачному серверу.

## 4. Определение состояния

Необходимо различать фактическое состояние процесса и предполагаемое состояние сессии.

Примеры состояний:

- Активна.
- Ожидает ввода пользователя.
- Ожидает подтверждения инструмента.
- Завершена.
- Ошибка.
- Неактивна.
- Неизвестное состояние.

Определение статуса должно по возможности опираться на реальные события Claude Code и информацию о процессе, а не только на анализ текста диалога.

Если достоверно определить состояние невозможно, приложение должно показывать неопределённость, а не выдавать предположение за факт.

Длительное отсутствие активности само по себе не является доказательством зависания.

## 5. AI-анализ

ИИ используется для интерпретации содержания сессий, а не для отслеживания каждого изменения файла.

Функции AI Analyzer:

- Генерация понятного названия задачи.
- Формирование краткой сводки сессии.
- Извлечение цели пользователя.
- Определение предполагаемого следующего шага.
- Выделение известных блокирующих факторов.
- Формирование краткого отчёта о завершённой работе.

Анализ должен выполняться по необходимости: при появлении новой задачи, существенном изменении контекста или запросе пользователя.

Для структурированных результатов используется валидация схемы.

ИИ не должен автоматически считать задачу завершённой только потому, что в истории появилось сообщение об успехе.

## 6. Техническая архитектура

### Backend

- Python.
- FastAPI для локального API.
- SQLite для хранения состояния и метаданных.
- Pydantic для валидации данных.
- Watchdog или аналогичный механизм для отслеживания файловых изменений.

### Frontend

- React.
- TypeScript.
- Компоненты Kanban-доски.
- Drag-and-drop.
- Обновление состояния без перезагрузки страницы.

### AI

- LangChain для интеграции с языковой моделью и описания инструментов.
- LangGraph для будущих многошаговых процессов и оркестрации.
- LLM API или совместимая локальная модель.

### Интеграции

- Claude Code — основной источник сессий.
- Git — контекст репозиториев и изменений.
- MCP — стандартизированный интерфейс доступа к функциям SessionFlow и внешним инструментам.

MCP не используется как обязательный транспорт для внутреннего обмена данными между всеми компонентами приложения.

## 7. Безопасность и приватность

SessionFlow изначально проектируется как локальное приложение.

Требования:

- История сессий не отправляется внешним сервисам без необходимости и соответствующей настройки.
- При использовании облачной LLM передаются только данные, необходимые для выбранного анализа.
- Секреты, токены и ключи API должны исключаться из анализа, насколько это технически возможно.
- Приложение не должно изменять файлы проектов без явного действия пользователя.
- Доступ к терминалу и выполнение команд не входят в полномочия первой версии.
- Данные и метаданные сессий должны храниться локально.
