# LovoGit — документация для разработки

Как работает агент и что он выдаёт. Что входит в первую версию — в [mvp.md](mvp.md).

## 1. Конвейер обработки

**Шаг 1. Подключение проекта.**
Пользователь указывает проекты при развёртывании своего экземпляра LovoGit (раздел 2). Агент анализирует файлы зависимостей, определяет используемые версии и формирует исходный профиль проекта.

**Шаг 2. Мониторинг.**
LovoGit периодически проверяет источники пакетов и релизов, отслеживая появление новых версий библиотек.

**Шаг 3. Анализ изменений.**
При обнаружении обновления агент изучает changelog, release notes и доступную документацию. Он выделяет изменения, которые могут повлиять на обратную совместимость или поведение библиотеки.

**Шаг 4. Сопоставление с кодом.**
LovoGit ищет в проекте использование затронутых функций, классов, методов и других элементов API.

**Шаг 5. Оценка риска.**
На основании найденных изменений и использования API агент определяет потенциальное влияние обновления на проект.

**Шаг 6. Уведомление.**
Telegram-бот присылает краткое уведомление с оценкой, причиной и ссылкой на официальный источник. Полный отчёт — затронутые участки кода, изменения, рекомендации и границы анализа — открывается кнопкой в Telegram Mini App.

## 2. Развёртывание и интерфейсы

**Self-hosted.** LovoGit — сервис, который разработчик или команда разворачивает у себя: один экземпляр на команду, свой Telegram-бот и несколько проектов. Все разрешённые чаты видят один общий набор проектов; разделения проектов по пользователям или чатам в MVP нет. Общего сервиса, куда подключаются чужие проекты, в MVP нет — это SaaS (см. [backlog.md](backlog.md)).

**Настройка — при развёртывании.** Проекты, токен бота и список `chat_id`, которым разрешён доступ, задаются конфигурацией экземпляра (файл или переменные окружения). Через бота и Mini App настройки не меняются.

**Telegram-бот — основной интерфейс.** Через него приходят уведомления, и у него есть команды для быстрых вопросов о проекте (ниже). Каждое уведомление самодостаточно для первого решения: зависимость, версии, оценка, причина одной строкой, ссылка на официальный источник и кнопка «Подробнее».

**Telegram Mini App — расширенный просмотр.** Экраны реестра и зависимости из [frontend.md](frontend.md). Открывается из меню бота или кнопкой из уведомления — сразу на нужной зависимости. Только показывает данные, анализ не запускает и ничего не меняет.

**Команды бота.** Отвечают на вопрос без открытия Mini App; где ответ длинный — кнопка «Подробнее» ведёт в Mini App. Статусы — из [frontend.md](frontend.md), раздел 2.

| Команда | Что делает |
|---|---|
| `/start` | Приветствие, кнопка открытия Mini App. Если `chat_id` нет в списке разрешённых — сообщает, что доступа нет, и больше ничего не показывает |
| `/status` | Общая сводка всех проектов: имя и ID, текущее число зависимостей, время и результат последнего запуска, причина ошибки, шесть счётчиков последнего успешного снимка с его временем. Нет оценок — явно сообщается. Команда не запускает проверку |
| `/attention` | Зависимости в статусах «Вероятна несовместимость», «Требует проверки», «Анализ не удался» — по строке на каждую, с кнопкой «Подробнее». Если таких нет — так и говорит, со ссылкой на границы анализа |
| `/dep <имя>` | Краткий отчёт по одной зависимости: версии, статус, причина, число затронутых мест, ссылка на официальный источник, кнопка «Подробнее». Неизвестное имя — сообщение об этом и похожие имена из проекта |
| `/check` | Запускает проверку вне расписания. Сразу отвечает, что проверка запущена (или что она уже идёт), по завершении — итог как у `/status`; новые находки приходят обычными уведомлениями |
| `/help` | Список команд |

Команды только читают данные и запускают проверку: настройки, проект и зависимости через бота не меняются. Ответы подчиняются тем же правилам, что и уведомления: факт отделён от предположения, «Низкий риск» не выдаётся за «совместимо». Список команд регистрируется в Telegram (`setMyCommands`), чтобы он был виден в меню бота.

**Следствия:**

- Экземпляр — постоянно работающий процесс: мониторинг по расписанию, отправка уведомлений, раздача Mini App и её API (`/api/registry`, `/api/dependencies/{name}`).
- Telegram открывает Mini App только по публичному `https://`-адресу, поэтому у экземпляра должен быть такой адрес.
- Доступ к API проверяется по `initData`: бэкенд проверяет подпись Telegram токеном бота и пускает только разрешённых пользователей. Отдельного логина нет.

## 3. Функциональные возможности

- Автоматическое обнаружение зависимостей проекта.
- Определение текущих и доступных версий.
- Фоновый мониторинг новых релизов.
- Анализ изменений между версиями.
- Поиск использования затронутого API в коде.
- Оценка потенциального риска обновления.
- Объяснение причин предупреждения.
- Ссылки на официальные источники информации.
- Уведомления о значимых обновлениях.
- История обнаруженных обновлений и результатов анализа.

## 4. Отчёт об обновлении

Пример: проект использует библиотеку `example-sdk` версии `1.8.2`. Вышла версия `2.0.0`, в которой удалён метод, используемый в нескольких файлах проекта.

Обычный мониторинг сообщает, что обновление доступно. LovoGit дополнительно находит вызовы удалённого метода и формирует отчёт:

| Поле | Значение |
|---|---|
| Зависимость | `example-sdk` |
| Текущая версия | `1.8.2` |
| Новая версия | `2.0.0` |
| Оценка | вероятна несовместимость |
| Причина | используемый проектом метод удалён в новой версии |
| Затронутые участки | конкретные файлы и строки, если их удалось определить |
| Рекомендация | проверить и адаптировать вызовы перед обновлением |

Разработчик заранее понимает, что требует внимания, а не узнаёт о проблеме после обновления и запуска приложения.

## 5. Принципы работы

**Практическая польза.** Каждое уведомление должно помогать принять конкретное решение, а не просто сообщать о новом релизе.

**Доказательность.** Выводы должны опираться на доступные источники и обнаруженные участки кода. Предположения необходимо отличать от подтверждённых фактов.

**Минимум ложных тревог.** Отсутствие обнаруженных проблем не гарантирует совместимость, поэтому система должна явно обозначать границы проведённого анализа.

**Автоматизация без потери контроля.** LovoGit помогает оценивать обновления, но окончательное решение об изменении зависимостей остаётся за разработчиком.

**Постепенное развитие.** Сначала продукт должен качественно решать ограниченный набор задач, после чего его возможности можно расширять.

## 6. Не решено

Описание продукта этого не задаёт — решить до начала соответствующей части:

- какие файлы зависимостей поддерживаются в MVP (`requirements.txt`, `pyproject.toml`, lock-файлы);
- откуда брать версии и release notes (PyPI, GitHub Releases, файлы `CHANGELOG`);
- как выполняется анализ изменений и поиск использования API (разбор AST, LLM или их сочетание);
- шкала оценки риска и её значения;
- как часто запускается проверка;
- как в конфигурации задаётся проект: локальный путь или URL репозитория;
- как экземпляр получает публичный HTTPS-адрес для Mini App (свой домен, туннель) — и что предлагать в инструкции по развёртыванию.


## 7. База данных и миграции

Engine и Alembic используют `DATABASE_URL` из окружения или `.env`. Значение по умолчанию — `sqlite+aiosqlite:///db.sqlite3`. Относительный путь разрешается от рабочего каталога: запускайте приложение и Alembic из корня проекта. Alembic не требует токены Telegram и LLM. Новая пустая база создаётся командой:

```sh
.venv/bin/python -m alembic upgrade head
```

Миграция `0001_baseline` создаёт существующие таблицы `repos` и `dependencies`; `0002_monitoring_state` добавляет историю. Внешние ключи SQLite проверяются каждым соединением приложения и миграций.

Для существующей SQLite без `alembic_version`:

1. Остановить приложение и сделать согласованную резервную копию SQLite (включая WAL либо через SQLite backup API). Сохранить копию отдельно от рабочей базы.
2. Сверить структуру с `alembic/versions/0001_baseline.py`: имена и типы столбцов, nullable, значения по умолчанию, первичные и внешние ключи. Существующие таблицы должны точно соответствовать baseline; `repos` содержит id/name/repo_url/created_at/updated_at/deleted_at, `dependencies` — id/repo_id/name/current_version/created_at/updated_at/deleted_at. Для просмотра используйте `sqlite3 db.sqlite3 '.schema'` и `PRAGMA table_info(...)`, `PRAGMA foreign_key_list(...)`. При отличиях остановиться и подготовить отдельный перенос. Stamp не проверяет структуру и не исправляет её.
3. Только после сверки явно зарегистрировать baseline и обновить схему:

```sh
.venv/bin/python -m alembic stamp 0001_baseline
.venv/bin/python -m alembic upgrade head
.venv/bin/python -m alembic current
```

Не выполняйте stamp автоматически при старте. Существующие проекты не получают выдуманных результатов: для них пока нет проверок и оценок.

Для отката остановить приложение, сохранить резервную копию, выполнить `.venv/bin/python -m alembic downgrade 0001_baseline` и вернуть предыдущую версию кода. Это удалит новую историю проверок, но сохранит проекты и зависимости. Не откатывайте baseline на рабочей базе. Миграции и stamp проверяются тестами на временных SQLite; рабочая база для тестирования не используется.

## 8. Контракт записи результатов мониторинга

Будущий исполнитель использует `MonitoringStateService(async_session_factory)`. Каждая операция открывает собственную сессию и транзакцию. Вызывающая сторона передаёт полный снимок проверенных зависимостей и пользовательскую причину ошибки, не содержащую SQL, токенов и трассировок; технические подробности записываются в журнал.

```python
from lovogit.app.services.monitoring import DependencyResultDTO, MonitoringStateService
from lovogit.db import DependencyStatus
from lovogit.db.engine import async_session_factory

state = MonitoringStateService(async_session_factory)
run_id = await state.start_run(project_id)
await state.succeed_run(run_id, [
    DependencyResultDTO("requests", "2.31.0", "2.32.0", DependencyStatus.REVIEW),
])
# Для сбоя другого, ещё не завершённого запуска:
# await state.fail_run(other_run_id, "Не удалось получить сведения о релизах")
```

`started_at` и `finished_at` можно передать явно как aware datetime; значения приводятся к UTC, в SQLite хранятся без смещения. По умолчанию используется текущее время UTC. Неизвестный проект отклоняется внешним ключом. Неверный статус, дубликаты имён после нормализации и пустая причина ошибки отклоняются; уже завершённый или отсутствующий запуск вызывает `RunTransitionError`. Ошибка записи откатывает всю операцию. Пустой успешный снимок допустим.

Состояние запуска (`running`, `succeeded`, `failed`) отличается от статуса зависимости. Успешный запуск может содержать зависимость со статусом `failed` — её анализ не удался. Завершённая история неизменяема через этот сервис. При падении процесса запуск остаётся `running`: восстановление будет задачей будущего исполнителя. Этот контракт сам не запускает анализ, не планирует проверки и не формирует дайджесты; примеры выполняются только при подключении реального конвейера, тесты используют временные БД.

## 9. Чтение сводки проектов

`StatusService(session).get_overview()` возвращает список `ProjectStatusDTO` без Telegram-разметки. Сервис одним запросом выбирает все неудалённые проекты, сортируя по имени и ID. `dependencies_count` — число текущих неудалённых зависимостей; шесть `status_counts` описывают состав последнего успешного снимка, поэтому после изменения состава проекта эти числа могут различаться.

`latest_run` — последний начатый запуск (время начала, затем ID), `latest_snapshot_at` — время завершения последнего успешного снимка, выбранного по тому же порядку начала запусков. Позднее завершение старой проверки не заменяет более новый снимок. Незавершённые данные не попадают в счётчики. При ошибке новой проверки сервис возвращает её причину и отдельно старый снимок; ошибка одного проекта не скрывает остальные.

Пустой список означает отсутствие проектов. `latest_run=None` означает отсутствие запусков. `status_counts=None` и `latest_snapshot_at=None` означают отсутствие успешного снимка; это не шесть нулей. Шесть нулей допустимы после успешной проверки без зависимостей. DTO содержат aware datetime UTC. Ошибка хранилища вызывает `StatusUnavailable` с исходной причиной в `__cause__`; транспорт логирует её и отправляет нейтральный ответ без технических подробностей.


## 10. Доступ и команда `/status`

В `.env` или окружении задаётся `ALLOWED_CHAT_IDS=[-1001234567890,123456789]` — JSON-массив целых чисел, включая отрицательные ID групп. Пустой список (значение по умолчанию) запрещает `/status` всем чатам. Все участники разрешённого чата получают одну сводку по всем проектам. Проверка происходит до открытия сессии БД; ID пользователя не влияет на доступ. Это правило реализовано для `/status`, защита остальных интерфейсов будет подключаться вместе с ними.

После миграций и настройки окружения бот запускается из корня проекта:

```sh
PYTHONPATH=src .venv/bin/python -m lovogit.bot.bot
```

Текущие обязательные настройки BOT_TOKEN и LLM-поля из `cfg/settings.py` сохраняются. Общая сводка содержит все активные проекты, сортируется по имени и ID и отправляется обычным текстом; длинная сводка разбивается на сообщения до 4096 единиц UTF-16 без потери данных. Отображается UTC. Старые оценки после ошибки или во время новой проверки помечаются как потенциально устаревшие. «Низкий риск» не гарантирует совместимость.

Если проектов нет — «Проекты не настроены» с пояснением о подключении при развёртывании. Если проверок нет — «Проверки ещё не выполнялись» и «Оценки обновлений пока нет». При недоступной БД — «Не удалось получить статус. Попробуйте позже»; технические подробности остаются в логе. Кнопок подробного просмотра и `/status <проект>` пока нет. Сам мониторинг, планировщик, новости и дайджесты по проектам не реализуются этим изменением.

Проверки выполняются без Telegram и внешних источников на временных базах:

```sh
PYTHONPATH=src .venv/bin/python -m unittest discover -s tests -v
node --test src/view/tests/logic.test.js
```

Для разработки используйте обычную сборку Python 3.14. В локальной free-threaded 3.14.4 воспроизводилось зависание завершения Alembic; проверки этого изменения выполнялись в отдельном обычном Python 3.14, без изменения рабочего окружения.

## 11. GitHub-исходники

GitHub-провайдер получает исходники независимо от Telegram, LLM и БД. Настройки
`GitHubSettings` читают окружение и `.env`: обязательный непустой `GITHUB_TOKEN`
(для выбранных репозиториев требуется чтение Contents), необязательный
`GITHUB_WORKSPACE_DIR` (по умолчанию системный temp). Публичность репозитория
не задаётся: используется один токен экземпляра.

Ограничения, все положительные: `GITHUB_CONNECT_TIMEOUT=10`,
`GITHUB_READ_TIMEOUT=30`, `GITHUB_DEADLINE=120` (секунды),
`GITHUB_MAX_ARCHIVE_BYTES=104857600`, `GITHUB_MAX_EXTRACTED_BYTES=524288000`,
`GITHUB_MAX_ENTRIES=50000`. Каталог workspace должен существовать и быть доступен
для записи. Настройки GitHub не загружаются при старте бота автоматически.

Адрес — только HTTPS URL корня github.com, допускаются `.git` и завершающий `/`.
Default branch берётся из GitHub, затем фиксируется SHA: обновление ветки во время
скачивания не меняет ревизию снимка. GitHub ID в результате отличается от ID
проекта в локальной БД.

Ошибки провайдера имеют безопасное `user_message`, `stage` и `status_code`.
`str(error)` содержит сообщение со стадией и HTTP-кодом для диагностики:
`InvalidRepoURL`, `AuthenticationError`, `RepoNotFound` (не найден или недоступен),
`RevisionUnavailable`, `RateLimited` (с `retry_at` UTC, если известно),
`SourceUnavailable`, `InvalidSourceResponse`, `InvalidArchive`,
`SourceStorageError`. Повторы не выполняются автоматически. Токен, тела HTTP-ошибок
и временные URL скачивания не включаются в сообщения ошибок. Redirect разрешён
только по HTTPS между api.github.com и codeload.github.com; токен передаётся
только api.github.com. Сырые журналы httpx/httpcore подавляются в контексте запросов провайдера,
чтобы временные URL и HTTP-заголовки не попадали в логи. Остальной HTTP-трафик
приложения продолжает логироваться с его обычными настройками.

Пример получения исходников (вызывать внутри асинхронной функции):

```python
import httpx

from lovogit.app.providers.github import GitHubProvider
from lovogit.app.services.repo import RepoService
from lovogit.cfg.github import GitHubSettings

settings = GitHubSettings()
async with httpx.AsyncClient() as client:
    source = RepoService(GitHubProvider(client, settings))
    async with source.open_source("https://github.com/team/project") as snapshot:
        print(snapshot.repo.commit_sha)
        # Читать файлы можно только внутри этого контекста.
        manifests = list(snapshot.root.rglob("pyproject.toml"))
```

`root` содержит файлы непосредственно от корня проекта. Каждый вызов владеет
отдельным временным каталогом: кэша и совместного использования каталогов нет.
Потребители только читают файлы; OS sandbox или read-only mount не создаётся.
Нормальный выход, ошибка и отмена освобождают каталог; распаковка в рабочем потоке
завершается до удаления. После аварийного завершения процесса в temp могут
остаться файлы, автоматический сборщик остатков пока отсутствует.

Архив не содержит историю Git. Submodules и LFS-объекты отдельно не скачиваются:
нельзя считать их содержимое полностью проанализированным. Исходники не
исполняются, зависимости не устанавливаются. `RepoService` не пишет в БД,
не создаёт зависимости и не запускает мониторинг. Регистрация проектов и разбор
манифестов будут подключаться отдельно.
