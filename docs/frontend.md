# SessionFlow — дизайн фронтенда (MVP)

Что должен уметь фронтенд и как он общается с бэкендом. Требования — в [mvp.md](mvp.md) и [dev-docs.md](dev-docs.md).

## 1. Что делает фронтенд в MVP

Одна страница:

- **Доска** из шести колонок (Inbox → Done) с карточками задач.
- **Фильтр по проекту** над доской.
- **Боковая панель задачи** — открывается по клику на карточку: описание, сессии, сводка ИИ, история статусов.
- **Перетаскивание** карточки между колонками.
- **Живое обновление** — карточки меняются без перезагрузки.
- **Баннер ошибок мониторинга** — если бэкенд не смог прочитать часть истории.

Фронтенд ничего не вычисляет сам: состояние сессий, названия и сводки приходят с бэкенда готовыми. Его задача — показать и передать действие пользователя.

## 2. Ключевое решение: доска показывает задачи

На доске лежат только **задачи** (Task). Каждая найденная сессия сразу получает задачу в колонке Inbox — это делает бэкенд.

Почему так:

- фронтенд работает с одним списком, а не склеивает задачи и сессии;
- колонка — это всегда `task.status`, статус сессии — всегда отдельный бейдж на карточке; перетаскивание меняет только первое;
- задача с несколькими сессиями (из спецификации) ложится в эту модель без изменений.

## 3. Стек

| Что | Чем | Почему |
|---|---|---|
| Сборка | Vite + React + TypeScript | стандарт, быстрый dev-сервер с прокси |
| Данные с сервера | TanStack Query | кэш, повторные запросы, оптимистичные обновления — не пишем руками |
| Типы API | `openapi-typescript` | типы генерируются из OpenAPI-схемы FastAPI, контракт в одном месте — Pydantic-моделях |
| Drag-and-drop | dnd-kit | поддерживается, работает с клавиатурой |
| Живые обновления | Server-Sent Events | поток нужен только от сервера к клиенту, браузер сам переподключается |
| Стили | CSS Modules | без дополнительной библиотеки |

Чего нет и не нужно в MVP: роутера (состояние экрана живёт в query-параметрах URL), глобального стейт-менеджера (серверное состояние — в TanStack Query, локальное — в `useState`), UI-кита, авторизации (сервер слушает только `127.0.0.1`).

Разработка: Vite проксирует `/api` на FastAPI (`localhost:8000`). В сборке FastAPI отдаёт статику фронтенда сам — один origin, CORS не нужен.

## 4. Структура кода

```
frontend/src/
  api/
    schema.d.ts     # сгенерирован из OpenAPI, руками не правится
    client.ts       # fetch-обёртка: базовый URL, JSON, ApiError
    projects.ts     # useProjects()
    tasks.ts        # useTasks(), useTask(), useMoveTask()
    sessions.ts     # useAnalyzeSession()
    events.ts       # подписка на SSE и инвалидация кэша
  board/            # Board, Column, TaskCard
  details/          # TaskPanel, SessionBlock
  shared/           # StatusBadge, RelativeTime, ErrorBanner
  App.tsx
  main.tsx
```

Правило: **компоненты не вызывают `fetch` и не знают URL**. Они берут хуки из `api/*.ts`. Всё знание об API — в папке `api/`, поэтому изменения API затрагивают одно место.

## 5. Контракт API

### Общие соглашения

- Префикс `/api/v1`. Внутри v1 изменения только добавляющие: новые поля, эндпоинты, значения перечислений. Ломающее изменение — это `/api/v2`.
- Списки возвращаются обёрткой `{ "items": [...] }` — пагинацию (`next_cursor`) можно добавить, не ломая клиентов.
- Ошибка — всегда `{ "error": { "code": "task_not_found", "message": "..." } }` с HTTP-статусом 4xx/5xx. `client.ts` превращает её в `ApiError`.
- Время — ISO 8601 в UTC, идентификаторы — строки.
- Поля в `snake_case`, как отдаёт Pydantic; фронтенд их не переименовывает.

### Эндпоинты MVP

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/v1/projects` | список проектов для фильтра |
| GET | `/api/v1/tasks?project_id=` | карточки доски |
| GET | `/api/v1/tasks/{id}` | всё для боковой панели |
| PATCH | `/api/v1/tasks/{id}` | смена колонки: `{ "status": "review" }` |
| POST | `/api/v1/sessions/{id}/analyze` | запросить сводку ИИ; ответ `202`, результат придёт событием |
| GET | `/api/v1/monitor` | состояние мониторинга и последние ошибки |
| GET | `/api/v1/events` | поток SSE |

### Модели

Типы ниже — эскиз для обсуждения. Источник правды — Pydantic-модели бэкенда, фронтенд получает их через генерацию.

```ts
type TaskStatus = "inbox" | "todo" | "in_progress" | "waiting" | "review" | "done";

type SessionStatus =
  | "active" | "waiting_input" | "waiting_approval"
  | "completed" | "error" | "inactive" | "unknown";

interface Project {
  id: string;
  name: string;
  path: string;
}

// Карточка на доске
interface TaskCard {
  id: string;
  title: string;                  // бэкенд подставляет запасное название, если ИИ недоступен
  status: TaskStatus;
  priority: "low" | "normal" | "high";
  project: { id: string; name: string };
  session: SessionSummary | null; // последняя по активности сессия задачи
  updated_at: string;
}

interface SessionSummary {
  id: string;
  status: SessionStatus;
  status_inferred: boolean;       // true — статус предположен, а не подтверждён событием или процессом
  last_activity_at: string;
  progress: string | null;
}

// Боковая панель
interface TaskDetail extends Omit<TaskCard, "session"> {
  description: string | null;
  result: string | null;
  created_at: string;
  sessions: SessionDetail[];
}

interface SessionDetail extends SessionSummary {
  project_path: string;
  created_at: string;
  last_operation: string | null;
  last_event: string | null;
  changed_files: string[] | null; // null — данных нет, [] — файлы не менялись
  resume_command: string;         // например `claude --resume <id>`, панель даёт его скопировать
  analysis: SessionAnalysis | null;
  history: { status: SessionStatus; at: string }[];
}

interface SessionAnalysis {
  summary: string;
  goal: string | null;
  next_step: string | null;
  blockers: string[];
  report: string | null;
  analyzed_at: string;
}

interface MonitorState {
  running: boolean;
  last_scan_at: string | null;
  errors: { at: string; source: string; message: string }[];
}
```

`null` у полей ИИ означает «анализа ещё нет» — интерфейс показывает это явно, а не пустую строку. Доска полностью работает без ИИ.

### События (SSE)

Каждое событие — конверт одного вида:

```
id: 1042
event: task.updated
data: {"id": "t_17"}
```

В MVP типов четыре:

| Событие | Что делает фронтенд |
|---|---|
| `task.created`, `task.updated` | обновляет список задач и открытую задачу |
| `session.updated` | обновляет список задач и открытую задачу (статус сессии виден на карточке) |
| `monitor.updated` | обновляет баннер мониторинга |

В событии только идентификатор, без данных. Фронтенд по нему инвалидирует нужные запросы в TanStack Query, и те перезапрашиваются. Это проще и надёжнее, чем вручную патчить кэш, а для локального приложения лишний запрос ничего не стоит.

Соответствие «событие → какие запросы обновить» — одна таблица в `api/events.ts`. После переподключения потока фронтенд инвалидирует всё: так нельзя пропустить события, пока соединения не было.

## 6. Поведение интерфейса

**Карточка** показывает: название, проект, бейдж статуса сессии, время последней активности («5 мин назад»), прогресс в одну строку. Если `status_inferred` — у бейджа знак «?» и подсказка «статус предположен». Статусы `error`, `waiting_input`, `waiting_approval` выделяются цветом — это «нужно вмешательство».

**Перетаскивание** меняет только `task.status`. Обновление оптимистичное: карточка переезжает сразу, при ошибке PATCH возвращается назад и показывается сообщение. Порядок внутри колонки — по `updated_at`, ручная сортировка не входит в MVP.

**Фильтр и открытая задача** хранятся в URL: `/?project=p_3&task=t_17`. Ссылку можно открыть заново, и экран восстановится.

**Ошибки**: ошибка загрузки доски — сообщение на месте доски с кнопкой «Повторить»; ошибка мониторинга — баннер сверху, доска при этом продолжает работать; оборванный SSE — небольшой индикатор «нет связи», браузер переподключается сам.

## 7. Как расширять

- **Новый эндпоинт:** бэкенд добавляет Pydantic-модель и маршрут → `npm run gen:api` обновляет `schema.d.ts` → в `api/<ресурс>.ts` появляется хук → компонент его использует.
- **Новый тип события:** строка в таблице `api/events.ts`.
- **Новый статус сессии:** бэкенд добавляет значение в перечисление. Фронтенд показывает незнакомый статус как `unknown` с исходным текстом, а не падает — так бэкенд можно обновлять раньше фронтенда.
- **Новое поле:** добавляется в модель, старый фронтенд его просто не использует.
- **Другие агенты (1.0):** у сессии появится поле `agent`, на карточке — значок агента. Остальной контракт не меняется.
- **MCP (0.4):** работает поверх тех же сервисов бэкенда, фронтенда не касается.

## 8. Тесты

- Vitest: `client.ts` (разбор ошибок), `events.ts` (событие → инвалидация), отображение статусов, включая незнакомый.
- Компоненты — через React Testing Library с замоканными хуками `api/`.
- E2E (Playwright) — после MVP.

## 9. Открытые вопросы

1. Какую сессию показывать на карточке, если у задачи их несколько: последнюю по активности (как сейчас в контракте) или ту, где нужно вмешательство?
2. Может ли пользователь вручную создать задачу без сессии (колонка Todo)? Если да — нужен `POST /api/v1/tasks` и форма.
3. Нужен ли ручной порядок карточек внутри колонки, или хватит сортировки по времени?
