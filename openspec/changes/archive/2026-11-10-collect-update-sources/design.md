# Design

## Context

См. `proposal.md` для мотивации. `PyPiProvider.get_package_info(package, version)` уже читает метаданные конкретного релиза и возвращает `PackageInfoDTO`: description/content type, project URLs, homepage, требования, dynamic и yanked. Провайдер владеет сетевыми ограничениями и типизированными ошибками. `RepoService` показывает существующий подход: отдельный сервис поверх переданного провайдера без БД.

Состояние comparer пока ожидает готовый `DependencyChange`, а его граф не исполняется. Сбор материалов не должен зависеть от этих заготовок. В действующих OpenSpec capabilities нет сбора источников обновлений; история мониторинга и GitHub-снимки остаются без изменений.

## Goals / Non-Goals

**Goals:**
- Дать вызывающему коду один законченный вызов для пары конкретных релизов.
- Сохранить исходные данные и происхождение, добавив детерминированные сведения о наличии материалов и различиях требований.
- Описать контракт, который следующий модуль сможет использовать для чтения источников, не превращая его сейчас в `DependencyChange`.

**Non-Goals:**
- Не расширять публичный API PyPI-провайдера и не добавлять обход сайтов.
- Не собирать промежуточные релизы, не выбирать последнюю версию, не вычислять совместимость constraints и не разрешать транзитивные зависимости.
- Не подключать результат к LangGraph, мониторингу, Telegram или хранилищу песочницы в этом change.

## Decisions

### 1. Сервис сбора поверх существующего провайдера

Добавить `UpdateSourceService` в `app/services/update_sources.py` с переданным `PyPiProvider` и единственной публичной операцией `collect(request)`. В `app/services/update_source_dto.py` определить запрос и DTO результата. Запрос содержит package, current_version, target_version; версии обязательны и не подменяются `None`.

Сервис последовательно вызывает `get_package_info` для current и target. Если строки запрошенных версий совпадают, допустимо получить метаданные один раз, но сформировать обе роли. Сервис не требует упорядоченности версий: он собирает переданную пару, включая prerelease или обратное сравнение. Корректность имени и URL-компонента версии остаётся в провайдере; непустые обязательные поля запроса проверяются до обращения к нему.

Альтернатива: включить сбор в PyPI-провайдер или узел графа. Отклонена: классификация ссылок и сравнение требований относятся к подготовке анализа, а не к HTTP API; привязка к незавершённому графу мешает отдельной проверке модуля.

### 2. Исходные метаданные плюс производные сведения

Результат содержит исходный запрос и две записи релиза. Каждая запись содержит роль current/target, полученный `PackageInfoDTO`, `description_available`, опубликованные ссылки и `has_change_links`. Для происхождения используются `source_kind=pypi_metadata`, роль, имя пакета и версия из ответа; запрошенная версия сохраняется отдельно от версии ответа. Опубликованные package_url/release_url остаются метаданными, а не доказательством фактического URL HTTP-запроса.

Общий результат содержит `has_change_links` как OR двух релизов и разницу требований. Значение description не очищается и не объединяется с другим релизом; strip применяется только для вычисления доступности. Оба релиза сохраняются даже при одинаковом тексте или ссылках.

Альтернатива: вернуть только найденный changelog. Отклонена: теряется README как возможный материал и невозможно отличить отсутствие changelog от неудачи получения метаданных.

### 3. Классификация по конечному списку явных названий

Каждая запись ссылки содержит исходные label и URL, поле происхождения `project_urls` или `home_page`, категорию и причину непригодности URL, если она есть. Для сравнения названия приводятся к lowercase с удалением пробелов, дефисов и подчёркиваний; остальные символы не удаляются. Начальный набор соответствий:

| Нормализованные названия | Категория |
|---|---|
| changelog, changes, history | changelog |
| releasenotes | release_notes |
| source, sourcecode, repository, code | source |
| documentation, docs | documentation |
| homepage, home | homepage |
| остальные | other |

Поле home_page имеет категорию homepage независимо от URL. Пустое/null home_page не создаёт отдельной ссылки. Пустой URL внутри project_urls сохраняется как непригодная запись. Нормализация label не меняет сохраняемое исходное значение.

Проверка пригодности требует абсолютный HTTP(S) URL с непустым hostname, допустимым port и без username/password. Строка с пробелами или управляющими символами непригодна. Причины: `empty_url`, `invalid_url`, `unsupported_scheme`, `credentials_not_allowed`. Запись сохраняет исходный URL; нет удаления query/fragment, посещения адреса или проверки доверия. Только пригодные changelog/release_notes учитываются в `has_change_links`.

Ссылки не дедуплицируются между ролями, чтобы не потерять происхождение. Неизвестные названия и ссылки сохраняются для следующего этапа.

Альтернатива: распознавать GitHub или `/releases` по адресу, использовать LLM либо искать changelog в README. Отклонена для первого модуля: это уже исследование источников. Известное имя — указание автора пакета, не подтверждение официальности ресурса.

### 4. Различия метаданных без семантических выводов

`requires_python` сравнивается как исходное optional string: разные значения означают только изменение опубликованного поля. `requires_dist` сравнивается как множества точных строк, добавления/удаления возвращаются в лексикографическом порядке для воспроизводимости. Исходные последовательности сохраняются внутри метаданных релиза. Markers, extras и specifiers не разбираются.

Если dynamic содержит `requires_dist`, результат помечает ограниченность требований соответствующего релиза. Null, уже превращённый провайдером в пустой tuple, не объявляется доказательством отсутствия реальных зависимостей. DTO не может восстановить различие null и пустого списка; публичный контракт провайдера ради этого не меняется.

Сведения target.yanked/target.yanked_reason передаются без замены версии и без превращения в статус совместимости. Пустая причина не отменяет признак отзыва.

Альтернатива: использовать resolver и семантическое сравнение ограничений. Отклонена: это другой модуль и потребовало бы контекста Python-окружения проекта.

### 5. Успешный результат только после получения обеих версий

Исключения `PackageNotFound`, `PyPiRateLimited`, `PyPiUnavailable`, `InvalidPyPiResponse` передаются без переупаковки, сохраняя version/status/retry_after. `ValueError` входа и cancellation также не маскируются. Автоматических retries, сохранения частичного результата и обращения к БД нет. Отсутствие материалов представлено флагами успешного результата, сетевые ошибки — исключениями.

Альтернатива: best-effort результат с одним релизом. Отклонена: downstream может ошибочно принять частичный сбор за полноценную основу сравнения.

## Risks / Trade-offs

- Авторы публикуют ссылки с произвольными названиями → сохранять other, ограничение классификации документировать; расширять словарь по отдельным примерам.
- Исторические метаданные содержат устаревшие ссылки → не объявлять адрес доступным, официальным или относящимся ко всему диапазону версий.
- Требования динамические или неполные → сохранять dynamic и не делать выводов о совместимости или фактическом окружении.
- Ссылки или описание отсутствуют → вернуть успешный сбор с явным отсутствием материалов; следующий модуль решает, как искать дальше.
- DTO провайдера не хранит HTTP endpoint запроса и различие null/пустого requires_dist → использовать доступное происхождение и явно ограничить выводы без расширения провайдера.

## Migration Plan

Добавляются только сервис, DTO, тесты и документация. Настройки, БД и действующие вызовы не меняются; включение в comparer выполняется будущим change. Откат состоит в удалении новых модулей и документации до появления потребителей. При реализации выполнить тесты нового сервиса, существующего PyPI-провайдера и полный набор unit-тестов; сеть для них не нужна.
