# Design

## Context

Мотивация и границы — в `proposal.md`. `app/providers/github.py` пуст. `BaseRepoProvider` требует одновременно `get_repo`, `download_repo` и `get_deps`; DTO содержат не относящуюся к снимку `release_version`. Единственный найденный потребитель — `RepoService.init_repo`, который вызывает `get_deps` перед записью проекта. Подключённого production-пути к этому сервису и тестов провайдера нет. Настройки Telegram/LLM обязательны в глобальном `_Settings`, но существующий модуль настроек БД уже показывает способ независимой конфигурации. История мониторинга и `/status` имеют собственные контракты и не требуют изменения.

## Goals / Non-Goals

**Goals:** дать вызывающему коду асинхронный контекст со стабильными метаданными и локальными файлами одной ревизии; сделать сеть подменяемой в тестах; явно определить владельца временных файлов.

**Non-Goals:** постоянный кэш исходников, регистрация проектов, GitHub Enterprise, SSH, выбор произвольной ветки, загрузка submodules/LFS-объектов, исполнение кода. Содержимое архивов submodules/LFS не считается полным исходным кодом этих объектов; это ограничение документируется для будущего анализа.

## Decisions

### 1. Отдельные контракты исходников

В `providers/dto.py` определить frozen DTO: `RepoRefDTO(owner, name, repo_url)`, `ResolvedRepoDTO(repo_id, full_name, repo_url, default_branch, commit_sha)` и `SourceSnapshotDTO(repo, root: Path)`. Слой данных явно обозначен суффиксом DTO. `repo_id` — GitHub ID, не локальный ID БД. Контракт провайдера: `resolve(github_url) -> ResolvedRepoDTO` и `snapshot(resolved_repo) -> AsyncContextManager[SourceSnapshotDTO]`. Snapshot принимает уже разрешённую ревизию и не разрешает ветку повторно. Клиент принадлежит вызывающему коду и передаётся провайдеру; провайдер его не закрывает. `RepoService` зависит непосредственно от `GitHubProvider`: ABC удаляется, поскольку других вариантов в текущей задаче нет. Внутренние зависимости имеют префикс `_`. Вызывающие методы располагаются выше вызываемых; публичные операции предшествуют вспомогательным.

Удалить устаревшие `release_version` и обязательный `get_deps` из контракта получения кода. Вместо сохранения через `init_repo` заменить пока не подключённый `RepoService` тонким фасадом `open_source(github_url)`: resolve, затем контекст snapshot. Он не пишет БД и не создаёт пустые dependencies. Обновить экспорты и проверить отсутствие старых вызовов. Это внутренняя несовместимость заготовки, а не изменение действующего пользовательского API. Альтернатива — возвращать пустой `get_deps` — скрывала бы отсутствие реализации.

### 2. URL и настройки

Принимать только `https://github.com/{owner}/{repo}` с необязательным `.git` и завершающим `/`. Проверять структуру до сети; не разрешать credentials, порт, query и fragment. Canonical identity после ответа GitHub брать из метаданных, чтобы учесть канонический регистр и переименование.

Добавить независимый `GitHubSettings` по образцу `DatabaseSettings`: `GITHUB_TOKEN: SecretStr` (обязателен, непустой), `GITHUB_WORKSPACE_DIR` (по умолчанию системный temp), лимиты. Не импортировать общий `cfg.settings` из провайдера. Токен не является полем проекта. Поддержку без токена не добавлять, чтобы не вводить второй путь доступа.

### 3. REST и архив по SHA

Использовать `httpx.AsyncClient` как прямую зависимость с явными таймаутами и отключённым автоматическим follow_redirects. Последовательность: метаданные репозитория, commit default branch (ref кодируется как один параметр пути), ZIP archive с ref, равным полученному SHA. Пустую/исчезнувшую ветку на стадии разрешения отображать в `RevisionUnavailable`.

GitHub archive endpoint возвращает redirect; ссылки приватных архивов временные. Это учтено по [официальной документации GitHub](https://docs.github.com/en/rest/repos/contents#download-a-repository-archive-zip). Не сохранять redirect URL, при каждом получении запрашивать новый. Разрешать только HTTPS, без credentials/нестандартных портов, с точными хостами `api.github.com` и `codeload.github.com`, максимум 5 redirects. Authorization устанавливать только для origin `https://api.github.com`; загрузочные запросы отправлять без него и без клиентских default credentials/cookies. Недопустимый redirect — отдельный код ошибки протокола получения.

Архив вместо clone: не требует git/SSH и не скачивает историю, которая пользователю сейчас не нужна. Встроенные автоматические retries отсутствуют: будущий исполнитель управляет повторами на основании ошибки и времени ожидания.

### 4. Время жизни и ограничения

`snapshot` создаёт уникальный приватный временный каталог, потоком скачивает ZIP и распаковывает в отдельный подкаталог. Только после полной проверки возвращает DTO. Общий префикс GitHub-архива снимается: `root` указывает непосредственно на файлы проекта. Не доверять именам архива при выборе внешнего пути.

Предлагаемые defaults: connect timeout 10 секунд, read timeout 30 секунд, общий сетевой deadline операции 120 секунд, ZIP до 100 MiB, распаковка до 500 MiB, до 50 000 записей. Положительные значения проверяются в настройках. Проверять реальные байты потока и распаковки, не только заголовки и ZIP metadata. Отклонять абсолютные пути, `..`, обратные разделители, ссылки/специальные файлы, повторные и конфликтующие пути, несколько корней и повреждённый ZIP. При отсутствии места возвращать локальную ошибку хранения. Тяжёлую распаковку вынести из event loop; при отмене дождаться остановки работы перед удалением каталога, чтобы фоновая запись не пережила cleanup.

Каталог доступен на время контекста для чтения. Контракт запрещает потребителям изменять файлы, но OS sandbox/read-only mount не вводится. При выходе, ошибке и отмене удалить принадлежащие операции данные; другие операции не затрагивать. Постоянного кэша и повторного использования каталогов нет: это исключает блокировки и гонки очистки.

### 5. Ошибки как данные для будущего исполнителя

Ввести семейство ошибок: invalid URL, authentication (401), not found or inaccessible (404 метаданных/обычный 403), revision unavailable, rate limited (429 или 403 с признаками лимита), transient (timeout, connection, 5xx), invalid response/archive, local storage. Ошибка лимита хранит `retry_at` UTC, когда его можно определить по Retry-After/reset. Rate-limit классификация предшествует обычному 403. 404 на стадии архива не выдавать за недоступность всего репозитория: это недоступная ревизия/архив.

Не включать сырые HTTP response bodies, заголовки, signed URLs и исходные HTTP exception repr в пользовательские ошибки и штатные логи. Строка исключения содержит стадию и status code при его наличии; `user_message` возвращает безопасный текст без технического контекста. Не логировать токен. Провайдер не меняет `MonitoringRun`: будущий исполнитель решит, как записать ошибку запуска.

## Risks / Trade-offs

- Архив крупного проекта может превысить лимиты → явная ошибка и настройки лимитов; потоковые проверки ограничивают потребление ресурсов.
- Default branch меняется между запросами → фиксировать SHA один раз; исчезнувшая ревизия завершает операцию ошибкой, следующий запуск разрешит актуальное состояние.
- Процесс убит без выполнения finally → штатная очистка гарантируется для обычного выхода/ошибки/отмены; после аварийного завершения допустимы остатки в temp. Автоматический сборщик остатков отложен.
- Архив не раскрывает Git LFS и submodules → обозначить ограничение, не заявлять полноту будущего анализа на основании этих объектов.
- Замена внутреннего RepoService убирает заготовку регистрации → реального подключённого потребителя нет; следующая capability регистрации будет строиться отдельно от извлечения зависимостей.

## Migration Plan

Добавить зависимость, настройки и новые контракты; заменить внутреннюю заготовку сервиса и экспорты в том же изменении. БД не мигрировать, текущие данные не трогать. Документировать пример асинхронного использования с освобождением клиента/снимка и настройку токена с доступом чтения содержимого нужных репозиториев. Запуск бота не должен автоматически скачивать код. Для отката вернуть код и lockfile предыдущей версии: постоянное состояние не меняется.
