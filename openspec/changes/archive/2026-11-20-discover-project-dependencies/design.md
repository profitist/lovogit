# Design

## Context

Мотивация — в proposal.md. `RepoService.open_source` уже предоставляет `SourceSnapshotDTO` с корнем и идентичностью GitHub-ревизии; временный каталог исчезает при выходе из контекста. Ни этот сервис, ни провайдер не должны автоматически менять инвентарь.

`RepoDependency` хранит только имя и обязательную строку `current_version`; `DependencyResult` тоже требует текущую версию и принадлежит завершению мониторинга. Эти схемы не вмещают диапазон, происхождение или неизвестность. `MonitoringStateService` публикует оценки, а не декларации зависимостей. Поэтому в этой итерации БД не используется.

В sandbox уже существует отдельная подготовка окружения через uv: она может разрешать диапазоны и измерять установленные версии. Это другой источник доказательств. Новый статический разбор не вызывает sandbox и не приписывает его гарантии результатам чтения файлов.

В проекте доступны Python 3.14, `packaging`, `tomllib` и `unittest`. Собственные `pyproject.toml` и `uv.lock` дают реальный пример обычного проекта PEP 621; текущий lock имеет `version = 1`, `revision = 3` и корневую запись с `source.virtual = "."`.

## Goals / Non-Goals

**Goals:**

- Получить воспроизводимый результат для одного корневого проекта без сети, LLM и исполнения кода.
- Сохранить декларации и доказательства отдельно от версии, пригодной для последующего запроса current/target.
- Дать тестируемые причины неполного разбора, неподдержанного lock, конфликта и неоднозначности.

**Non-Goals:**

- Не определять состав production/venv по декларациям и не утверждать, что пакет импортируется кодом.
- Не реализовывать resolver, оценку markers для конкретного окружения, полный граф транзитивных зависимостей или синхронизацию таблиц.
- Не поддерживать Poetry/Pipenv, setup.py/setup.cfg, pylock.toml, workspace, рекурсивное обнаружение проектов и dependency-groups в первой версии. Optional-dependencies PEP 621 при этом входят в результат как отдельные области, без автоматического включения в runtime.

## Decisions

### 1. Пакет зависимостей с функциями и явным входом

Создать `app/dependencies/`: `inventory.py` для операции `read_dependency_inventory(snapshot, *, source="auto", limits=None)`, `dto.py` для результата, `pyproject.py`, `requirements.py` и `uv_lock.py` для самостоятельных форматов. Общую нетривиальную работу с путями и бюджетами держать в `files.py`, проверку pins и ограничений — в `versions.py`. Не добавлять класс-сервис на одну функцию, фабрику парсеров, ABC или registry плагинов.

Все вызовы выполняются на готовом снимке. Результат содержит значения и относительные пути, а не открытые файлы и ленивые обращения к каталогу. Для async вызывающего документировать `asyncio.to_thread` внутри `open_source`, до освобождения снимка. Разбор остаётся отдельной синхронной ограниченной операцией.

Альтернатива — добавить парсер в GitHubProvider или RepoService. Отклонена: источник снимка не определяет формат зависимостей; разделение уже закреплено существующей спецификацией. Добавление в agent тоже не подходит: здесь нет задачи для LLM.

### 2. Явный выбор одного корневого манифеста

`source` принимает `auto`, `pyproject`, `requirements`. В auto сначала исследуется корневой pyproject: при таблице `project` он является источником, даже если dependencies отсутствует или пуст. Если pyproject корректен, но таблицы project нет, возможен переход к requirements. Неверный TOML не маскируется fallback. Явно выбранный отсутствующий файл даёт failed с `missing_source`.

Доступные невыбранные файлы перечисляются в результате. Самостоятельные `requirements-dev.txt`, `requirements/*.txt` читаются только через включения из выбранного requirements; других entrypoint в этой версии нет. При requirements uv.lock остаётся невыбранным, так как связь с ним не доказана.

Альтернатива — объединить все найденные файлы. Отклонена: это смешивает разные сценарии установки, exports и несовместимые окружения. Явный source позволяет выбрать requirements без эвристики.

### 3. Контракт результата и нормализация

DTO результата хранит repo identity/SHA, выбранный source, обнаруженные файлы и их disposition, прочитанные файлы, декларации, constraints, diagnostics и статус. Для файлов, участвующих в выводе, сохранять SHA-256 прочитанных байтов; это происхождение результата, не проверка свежести lock.

Декларация содержит original/normalized name, raw requirement, source kind, specifier, extras, marker, scope (`runtime` или `extra:<name>`), provenance, `version_state`, `current_version`, `reason` и lock candidates. Provenance — относительный путь и TOML key с индексом либо начало/конец строк requirements. Constraints хранятся отдельно и ссылаются на места применения. Диагностика имеет стабильный code, severity и место; в текст ошибки не копировать секреты, URL с credentials или содержимое целого файла.

Имена и extras нормализуются по правилам packaging; версии проверяются как PEP 440, требования — как PEP 508. Повторы с одинаковыми scope, marker, extras и specifier объединяются с сохранением всех мест. Разные scope/условия не схлопываются в единственную запись имени. Совместимые ограничения одной безусловной области собираются вместе; противоположные pins дают conflict. Решать общую выполнимость произвольного диапазона без конкретного кандидата не требуется.

Статус разбора независим от `version_state`: корректный диапазон — complete + unresolved. Unsupported записи/директивы, динамические поля и проблемы выбранного lock дают partial; нечитаемый/неразбираемый выбранный корень — failed; нет поддержанного источника — no_sources. Ошибки программиста и отмена не преобразуются в пустой инвентарь. Сортировка деклараций, origins и diagnostics детерминирована.

Альтернатива — вернуть `dict[name, version]` или заполнить RepoDependency. Отклонена из-за потери условий, конфликтов и причин неизвестности; миграция БД не нужна для полезного автономного этапа.

### 4. Requirements — ограниченное подмножество pip

Поддержать UTF-8 с необязательным BOM, пустые строки, комментарии с учётом URL fragments, backslash continuation и именованные PEP 508 строки. Inline `--hash=...`/`--hash ...` отделяются от требования и сохраняются без проверки артефактов. Формы включений: `-r path`, `-rpath`, `--requirement path`, `--requirement=path` и соответствующие формы `-c`/`--constraint`.

Включение `-r` разбирает целевой файл как требования, `-c` — как ограничения; контекст включения входит в идентичность обработки. Все constraints выбранного requirements-набора применяются независимо от порядка строк, но не создают зависимости. При безусловном exact constraint и совместимом требовании возможен declared_pin; условные constraints сохраняются и не делают безусловную версию однозначной. При необходимости оставлять unresolved с `conditional_constraints`, не пытаться решать пересечения условий.

Глобальные опции установки, env substitutions, URL includes, произвольные локальные archives и неименованные установки — диагностируемые неподдержанные записи. Именованные direct references и editable строки сохраняются насколько возможно как unsupported, без обращения к цели. `===` с произвольным не-PEP-440 значением не становится current_version. Подмножество и причины описать в пользовательской документации.

Альтернатива — импортировать внутренний parser pip или запускать pip/uv. Отклонена: внутренний API нестабилен, а запуск пакетного менеджера усложняет детерминированность и выходит за выбранную границу чтения.

### 5. Версия — подтверждение из файла, а не installed evidence

`version_state` принимает declared_pin, locked, unresolved, conflict, unsupported. Current_version — nullable. `==X` без wildcard и с допустимой PEP 440 версией даёт объявленную фиксацию, если остальные совместно применимые ограничения ей не противоречат. Дополнительные совместимые ограничения не снимают фиксацию. `==X.*`, диапазон и отсутствие specifier остаются unresolved без подходящего lock. `===X` принимается как declared_pin только при PEP 440 X и точной совместимости остальных ограничений; иначе unsupported.

Не выбирать latest из PyPI и не интерпретировать нижнюю границу как baseline. Если найденный lock повреждён или несогласован, не откатываться молча к declared_pin: сохранить pin как декларацию, lock candidates как сведения и вернуть неподтверждённую версию с причиной. Это предотвращает скрытое расхождение между двумя файлами.

Markers не вычисляются и никогда не дополняются значениями хоста. Версия условной декларации, если доказана, остаётся условной; единственной версии пакета для всего проекта не формируется. Проверка реального окружения потребует отдельного входа установленного состава или sandbox.

### 6. Консервативное чтение uv.lock

Начальный поддержанный layout — TOML `version=1, revision=3` для обычного корневого проекта с единственной local root entry (`source.virtual="."` или `source.editable="."`). Остальные version/revision явно дают `unsupported_lock_version`. Ограничение layout документируется и тестируется; расширение поддержки — изменение парсера и fixtures, без попытки угадать неизвестный формат.

Проверить имя корневого проекта, его metadata.requires-dist против статических деклараций PEP 621 (включая extras/markers и optional-группы), а также requires-python. Сравнивать нормализованные составы, а не порядок; при невозможности доказать эквивалентность вернуть `lock_metadata_mismatch` или `unsupported_lock_metadata`. Учитывать корневые зависимости и optional-dependencies при выборе связанных package entries. Workspace, динамические поля, override-dependencies, constraint-dependencies и изменяющие source настройки tool.uv в этой версии не разрешаются: диагностировать и не подтверждать lock-версии.

Registry-записи проверяются по имени, версии, принадлежности прямому ребру и совместимости specifier. Все подходящие записи/условия остаются candidates. Несколько различных версий означают `ambiguous_lock`; сложные resolution-markers, условия рёбер и неоднозначные sources, которые parser не может надёжно сопоставить, дают unresolved с конкретной причиной. Допустима консервативная неизвестность даже для корректного сложного lock. Простая единственная применимая registry-запись даёт locked; отсутствие прямого ребра/пакета — `missing_lock_entry`, противоречие — conflict. Транзитивные пакеты не расширяют список прямых зависимостей.

Эта проверка — согласованность поддержанных деклараций и lock в одном снимке, не замена `uv lock --check`, не доказательство полной корректности решения и не измерение установки. Нельзя подтверждать свежесть только по имени и попаданию версии в диапазон. Перегенерировать lock или вызывать uv export запрещено.

Альтернатива — читать только name/version из всех package entries. Отклонена из-за универсальных lock, транзитивных пакетов, stale metadata и нескольких sources. Полная реализация resolver/всей семантики uv тоже отклонена: это отдельный, существенно больший проект.

### 7. Бюджеты и ошибки файлов

Общий reader ограничивает до 128 уникальных файлов, 16 уровней включения, 8 MiB на файл, 32 MiB суммарно прочитанных байтов и 100 000 логических записей. Значения можно явно уменьшить/изменить через DTO limits; отрицательные и нулевые бюджеты отклоняются до чтения. Повторный доступ использует кэш байтов, но обработка и происхождение учитывают режим requirement/constraint.

Пути разрешаются относительно включающего файла и проверяются относительно root; абсолютные/удалённые пути, symlink в любой части и специальные файлы отклоняются. Ссылки `..` внутри корня допустимы. Цикл отслеживается по активному стеку `(path, mode)`, а не запрещает легальное повторное включение. Контракт предполагает неизменяемый снимок на время операции, как у GitHub snapshot.

Ожидаемые I/O, syntax и format errors попадают в diagnostics с местом; ошибки локальной строки не скрывают остальные корректные декларации. Отказ в выбранном корневом источнике даёт failed; сбой включения или lock — partial. При лимите дальнейшее чтение прекращается, complete не возвращается.

Альтернатива — довериться только лимитам GitHub archive. Отклонена: локальный вызов тоже принимает файлы, а граф включений имеет собственные циклы и расширение числа обработок.

## Risks / Trade-offs

- Универсальные и меняющиеся форматы uv → явный поддержанный layout, candidates и conservative unresolved; fixtures на metadata, fork markers и неизвестную revision.
- Декларации не доказывают deployment → происхождение declared_pin/locked и отсутствие installed claim во всех примерах.
- Ограниченное подмножество pip → diagnostics вместо молчаливого пропуска; unsupported не становится пустым успехом.
- Несколько манифестов могут описывать разные окружения → один явный source и список невыбранных файлов; без автоматического merge.
- Инвентарь не сохраняется в существующую таблицу → полезен через публичную функцию и локальный отчёт; хранение расширенных данных и запуск мониторинга планируются отдельно.

## Migration Plan

Изменение аддитивное: добавить пакет, тесты и docs без миграций БД и изменения существующих вызовов. Документировать вызов внутри `RepoService.open_source` с готовым snapshot и проверить на fixture и собственном проекте без сети. Существующие незакоммиченные изменения comparer не включать в реализацию этого change.

Откат — прекратить вызовы новой функции и удалить добавленный пакет; прежнее получение снимка, сохранённые результаты и bot-команды не затрагиваются.
