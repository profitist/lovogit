# Design

## Context

Мотивация — в `proposal.md`. Сейчас `commands.py` содержит незащищённую заглушку `/add_repo`; `bot.py` подключает общий роутер раньше защищённых команд. `Repo` хранит локальный ID, имя, URL и `deleted_at`, но не имеет уникального ключа внешнего репозитория. `RepoService.open_source()` намеренно не регистрирует проекты. `GitHubProvider.resolve()` уже возвращает стабильный GitHub ID, канонический URL и имя, проверяя default branch и SHA без скачивания архива. `GitHubSettings` изолирован от LLM; бот пока не создаёт GitHub-клиент.

Существующие тесты создают записи с URL `url`; миграция не должна пытаться валидировать или разрешать прежние адреса через сеть. `/status` и `/attention` уже корректно показывают проекты без запусков, но их пустые состояния и документация обещают подключение при развёртывании. Новое решение пользователя — подключение через бота; прежнее ограничение нужно явно снять.

## Goals / Non-Goals

**Goals:** стабильная идентичность проекта и атомарная регистрация, независимый от Telegram сервис, существующий контракт ошибок GitHub, отсутствие сетевых операций в транзакции БД.

**Non-Goals:** расширение `RepoService` регистрацией, изменение провайдера снимков, хранение SHA как результата анализа, автопроверка после добавления, отдельные роли доступа и управление списком через Mini App. Агентская часть не меняется.

## Decisions

### Команда и правила доступа

Один аргумент: `/add_repo https://github.com/owner/repo`. Имя берётся из `full_name`, отдельный пользовательский alias не вводится. Это устраняет неоднозначность одинаковых коротких имён из разных организаций. Все участники разрешённых чатов могут добавлять репозитории: текущая модель доступа командная, администраторские роли были бы новой задачей.

Добавить отдельный роутер `bot/add_repo.py` и middleware доступа. До открытия сессии и обращения к GitHub проверять chat_id; после этого разбирать аргументы и URL. Удалить заглушку из общего роутера, подключить новый роутер в `bot.py`. Проверять Dispatcher со всеми действующими роутерами, чтобы общий обработчик не обходил защиту.

### Проверка существующим провайдером

Сервис `RepositoryRegistrationService` в `app/services/registration.py` получает `GitHubProvider` и фабрику сессий. Операция `add_repository(url)` валидирует URL, вызывает `resolve`, затем открывает короткую транзакцию. Архив не скачивается. Не вводить второй HTTP-клиент метаданных и дублирующую обработку ошибок. Следствие выбранного подхода: пустой репозиторий без доступной основной ревизии пока нельзя зарегистрировать; это закреплено спецификацией.

В `bot.py` создать один `httpx.AsyncClient` на время работы бота, собрать провайдер из `GitHubSettings`, закрыть клиент при завершении и ошибке запуска. Настройки GitHub становятся обязательными при запуске бота с регистрацией; ошибка конфигурации должна возникать до polling. Импорт модулей не должен читать GitHub-настройки. Никаких новых LLM-настроек или зависимостей.

### Стабильная идентичность и совместимость

Добавить `Repo.github_id` как nullable целое с уникальным ограничением для всех ненулевых значений, включая удалённые записи. Локальный `Repo.id` сохраняет роль ключа внешних связей. GitHub ID надёжнее URL при переименовании и переносе репозитория. Один уникальный URL без GitHub ID не решает эту задачу.

Миграция `0003_repository_identity` добавляет поле и уникальный индекс, без сети, backfill и изменения старых строк. NULL разрешён для старых записей и существующих тестов. Удаление поля при downgrade не затрагивает проекты, зависимости и историю.

После `resolve` в SQLite начинать короткую write-транзакцию `BEGIN IMMEDIATE` до чтения кандидатов, чтобы конкурентные операции не читали одинаковое старое состояние. Сначала искать GitHub ID; также проверять совпадения нормализованного URL входного адреса и канонического адреса, сравнивая owner/repo без учёта регистра. Невалидные старые URL не считать совпадениями. Если совпадения указывают на разные записи либо иной известный GitHub ID — выдавать конфликт без объединения. Единственную старую запись с NULL ID привязать; иначе создать новую. Удалённую запись восстановить, метаданные актуализировать, историю не менять.

Уникальный индекс остаётся окончательной защитой целостности. Ожидаемый конфликт вставки по GitHub ID обрабатывать после rollback повторным чтением победившей записи; другие ошибки БД не выдавать за успешный дубль. Обычный SQLite busy timeout остаётся ограничением ожидания: исчерпание означает безопасную ошибку хранения с возможностью повторить команду. Не держать транзакцию при сети или отправке Telegram.

### Результат и доставка

Возвращать неизменяемый DTO с локальным ID, именем, URL и исходом `added`, `already_tracked`, `restored`. Обновление метаданных активного проекта по прежнему GitHub ID возвращает `already_tracked`. Транспорт показывает соответствующее подтверждение, ID и «Анализ не запущен» с `parse_mode=None`. Commit происходит до подтверждения; ошибка Telegram не отменяет запись. Сервис не зависит от объектов бота.

Безопасные причины `SourceError.user_message` показывать без сырых ответов GitHub; для `RateLimited` добавить `retry_at` в UTC, если известно. Ошибки БД оборачивать в отдельное исключение с исходной причиной; отвечать нейтрально и логировать без URL с credentials, токенов и тела ответа. Конфликт прежних записей требует ручного исправления администратором, но не SQL в ответе.

## Risks / Trade-offs

- Пустой репозиторий отклоняется → честное объяснение отсутствия ревизии; metadata-only регистрация может стать отдельным расширением.
- Запрос GitHub нужен и при повторной команде → это проверяет текущий доступ и новое каноническое имя; при сбое прежняя запись не меняется.
- Старые данные могут содержать дубли → не сливать автоматически и не терять историю, вернуть понятный конфликт.
- При восстановлении появятся прежние оценки → сохранить их даты и действующие предупреждения об актуальности, не выдавать их за новый анализ.
- Разрешённый чат получает право записи → явно описать командную модель в `/help` и документации.
- Free-threaded Python ранее вызывал таймауты Alembic → миграционные и интеграционные проверки выполнять на обычном Python 3.14 при воспроизведении известного ограничения.

## Migration Plan

Сначала применить `alembic upgrade head`, затем развернуть бот с `GITHUB_TOKEN` и существующим `ALLOWED_CHAT_IDS`. Существующие строки не меняются до явной регистрации. Проверить добавление, повтор и `/status`. При откате остановить бот, вернуть предыдущий код; downgrade удаляет только новый индекс и GitHub ID, сохраняя локальные проекты и историю. Перед downgrade сделать резервную копию: повторное развёртывание потребует снова привязать внешние ID.
