# Design

## Context

См. proposal.md для мотивации. Вход `UpdateSourceFetchResultDTO` уже содержит исходный запрос, метаданные и tuple результатов с text/content_type/links/final_url. HTML пока сохранён без очистки. Основные спецификации прямо отделяют загрузку от анализа.

Comparer — незавершённая заготовка, его `DependencyChange` содержит строки changed_api/change_description. Prompt поиска уже упоминает поведение и настройки. Поэтому новый список утверждений не подгоняется под одиночную строку: адаптация comparer будет отдельным change.

`agent/core.py` не возвращает созданных агентов и импортирует глобальные настройки, требующие токен бота; там также расходятся CHEAP_MODEL и MODEL_CHEAP. Новый сервис не использует этот путь. LangChain и Pydantic уже присутствуют в зависимостях, но готового адаптера анализа нет.

## Goals / Non-Goals

**Goals:** воспроизводимая проверка ответа модели по переданным текстам; сохранение неопределённости версий и покрытия; независимый импорт и тестирование без секретов.

**Non-Goals:** подтверждение истинности changelog, доказательство семантического соответствия цитаты выводу, получение полной истории релизов, сравнение исходников библиотеки и агрегация оценок риска.

## Decisions

### 1. Самостоятельный сервис и внедряемая модель

Добавить `app/services/update_source_analysis.py` с `UpdateSourceAnalysisService.analyze(fetched)`, frozen DTO в `update_source_analysis_dto.py`. Сервис получает адаптер модели и настройки через конструктор. `agent/update_sources/extractor.py` содержит `UpdateChangeExtractor`, `schemas.py` — Pydantic-схемы ответа модели, `prompts.py` — системные инструкции.

Адаптер принимает явно созданную вызывающим LangChain chat model, вызывает её асинхронно без инструментов и ожидает JSON. Не создаёт модель по глобальным settings; производственные credentials/provider/model выбираются вызывающим при сборке приложения. Для этого change достаточно публичного вызова с готовой моделью и документированного примера; автоматическая фабрика провайдеров не добавляется. Прямая зависимость packaging нужна для сравнения версий. Изменение agent/core.py отвергнуто как отдельная ответственность.

### 2. Документы обрабатываются по одному

В исходном порядке results выбирать только fetched с непустым text; каждому присвоить стабильный внутри вызова ID по позиции результата. Одна запись результата загрузки — один документ, даже если у неё несколько links. Сохранять полный исходный fetched и карту ID → links/final_url. README и requirements_diff остаются контекстом результата, но не превращаются в утверждения этого текстового анализа.

Для первой версии передавать исходный текст, включая HTML, без очистки, обрезания и разбиения. Это обеспечивает однозначную проверку точных цитат. Слишком большой документ целиком пропускается с причиной; произвольное усечение, извлечение HTML и chunking отвергнуты до появления отдельного контракта отображения цитат на оригинал. Prompt сообщает media type и требует игнорировать HTML-разметку как инструкции; HTML не исполняется.

### 3. Результат и проверка утверждений

Ответ документа: JSON object с changes (не более 100 записей) и limitations (не более 20 строк). Каждая запись: category (`api`, `behavior`, `configuration`, `default_value`, `python_requirement`, `dependency_requirement`), description, symbol|null, release_version|null, evidence (1–5 пар source_id/quote) и version_evidence (source_id/quote|null). Схемы запрещают лишние поля, задают максимальные длины description 2000, symbol/version 300 и quote 4000 символов. Нет полей compatibility, risk или confident=true.

Внешний JSON/общая схема неверны → failed/invalid_response для документа. Отдельные записи валидировать независимо: неверная схема записи, источник, пустая/отсутствующая цитата → rejected с индексом и причиной; остальные сохраняются. Evidence может ссылаться только на текущий документ, поскольку остальные тексты не передавались этому вызову. Проверять точное вхождение quote в отправленный оригинал, сохранять вычисленные позиции первого совпадения и исходные links; URL из ответа модели не принимать. Непустой symbol принимать только при буквальном присутствии в evidence, иначе отклонять запись с unsupported_symbol.

Сравнивать границы через packaging.version.Version; непустое имя пакета и согласованность идентичности current/target также проверить до LLM. InvalidVersion или current >= target → ValueError с контекстом, без вызова модели. Модель видит нормализованные границы и инструкцию учитывать все промежуточные релизы.

Для конкретной release_version требовать version_evidence с точной цитатой и буквальным присутствием указанной версии внутри неё. Затем программно проверять `(current, target]`. Известная версия вне диапазона → rejected/outside_interval. Непарсируемая версия, отсутствие подтверждения версии или release_version=null → сохранить валидное содержательное утверждение в unscoped_changes с причиной unknown_version; не включать его в changes. Привязка цитаты к разделу релиза остаётся интерпретацией модели и явно отмечается этим ограничением.

Точное совпадение цитат не доказывает семантическую корректность. Противоречащие утверждения разных документов сохраняются отдельно, со своим происхождением; семантическое объединение не выполняется.

### 4. Покрытие и состояния

Результат содержит исходный fetched, changes, unscoped_changes, rejected, записи документов (`processed`, `skipped`, `failed` с причинами), observed_versions из принятых утверждений и ограничения. Статус: no_materials (нет подходящих непустых fetched), failed (ни один вызванный документ не обработан успешно), partial (есть обработанные документы, но также failed, исключения по лимитам или rejected), completed (все выбранные документы обработаны без таких потерь). Если все кандидаты пропущены по лимитам, статус partial без вызовов. Наличие unscoped_changes явно добавляет limitation unknown_version и даёт partial.

Покрытие всего интервала всегда `undetermined` в этой версии: список всех существующих релизов не запрашивается и не присутствует во входе. observed_versions — только наблюдения, не полный список. Даже completed с пустыми changes не означает отсутствия изменений; это отражается в постоянных limitations. Явные ошибки загрузки/пропуски входного fetched наследуются как ограничения и дают partial, если есть обработанные документы. При полностью отсутствующем входном тексте используется no_materials независимо от причин загрузки.

### 5. Лимиты и отказоустойчивость

Независимые `SourceAnalysisSettings` в cfg/source_analysis.py: максимум 10 документов, 60000 символов документа, 180000 символов суммарно, 60000 символов ответа, timeout вызова 30 с, общий deadline 120 с. Все значения положительные. Обрабатываются целые документы последовательно; при превышении суммарного бюджета документ пропускается, следующий меньший документ может поместиться. Один вызов на выбранный документ, без автоматических retries или исправляющих запросов. Модель вызывающего должна быть сконфигурирована с собственным конечным лимитом output tokens; документация подчёркивает, что проверка длины полученного ответа сама не ограничивает расход токенов провайдера.

Prompt отделяет системную задачу от пользовательского сообщения с сериализованными данными документа, не предоставляет tools и не включает секреты/код проекта. Ошибки адаптера с контекстом source_id преобразуются в failed/model_error, refusal → failed/refused, превышение ответа → failed/response_limit, неверный JSON → failed/invalid_response. Timeout → failed/timeout. Не ловить общий Exception вокруг всего сервиса; неожиданные ошибки программирования не скрывать. Внешний CancelledError проходит наружу. После общего deadline текущий документ получает timeout, оставшиеся кандидаты skipped/deadline_exceeded. Модель/её клиент принадлежат вызывающему и сервисом не закрываются.

## Risks / Trade-offs

- [Версия в цитате не гарантирует правильную привязку изменения к разделу] → сохранять version_evidence и ограничения; качественную оценку проводить на ручных фикстурах, не обещать доказательство.
- [HTML и длинные changelog хуже помещаются в бюджет] → явные пропуски; очистка/разбиение потребуют следующего change.
- [Отсутствуют инструменты для проверки полноты истории] → coverage=undetermined независимо от статуса выполнения.
- [Невалидный ответ или prompt injection модели] → отсутствие инструментов, строгая локальная проверка и регрессионные фикстуры; это ограничивает действия, но не гарантирует правильность текста модели.

## Migration Plan

Добавление сервиса и документации без миграций БД и изменения существующих DTO. Сначала подменённая модель в тестах; готовность не зависит от платных live-вызовов. Ручная оценка на реальной модели возможна отдельно при наличии настроенного экземпляра. Откат — прекратить вызов нового сервиса; глобальное состояние не меняется.
