# Design

## Context

См. proposal.md для мотивации. `DependencyDeclarationDTO` уже содержит source_kind, version_state, nullable current_version, specifier, constraints, marker, scope и provenance. Обязательный current для анализа из диапазона получать нельзя.

`PyPiProvider.get_package` возвращает `PackageIndexDTO.versions` без сортировки и фильтрации. `get_package_info(package, version)` читает конкретный релиз и предоставляет name, version, yanked, yanked_reason и requires_python. Провайдер уже ограничивает каждый HTTP-запрос, закрывает responses и предоставляет типизированные ошибки без закрытия переданного AsyncClient. Проверка имени в нём есть, но соответствие возвращённой версии запрошенному кандидату отдельно нужно проверить в селекторе.

`collect_sources` принимает `UpdateSourceRequest` с явной парой. Существующий spec запрещает ему выбирать версии: новый шаг располагается перед сбором, не меняя этот контракт. `packaging` уже используется в инвентаре и анализе; новых зависимостей не требуется.

## Goals / Non-Goals

**Goals:**

- Дать одну запускаемую операцию «декларация → решение о target», пригодную для будущего конвейера.
- Сделать правило MVP однозначным и тестируемым, включая отсутствие обновления, исключение yanked и ограничение числа запросов.
- Сохранить контекст декларации и выбранного релиза для анализа, не смешивая выбор версии с оценкой риска.

**Non-Goals:**

- Не вычислять окружение, разрешимость зависимостей, доступность подходящего wheel или удовлетворение диапазону проекта.
- Не добавлять batch API, общий cache, планировщик, запись в БД, бот-команды, автоматический вызов LLM и полный workflow comparer.
- Не менять схемы или DTO провайдера и не вводить альтернативные настраиваемые стратегии выбора.

## Decisions

### 1. Одна функция и небольшие DTO в обычном модуле

Создать `app/update_selection.py` с `select_latest_stable_update(dependency, provider, *, max_release_checks=32, timeout=120)`. Dependencies передаются явно; provider и его клиент принадлежат вызывающему. Нет класса-сервиса, ABC и новой конфигурационной подсистемы. Локальные аргументы бюджетов проверяются до сети: положительный целый лимит проверок и положительное конечное время.

В модуле разместить DTO результата и исключённого релиза: это один слой данных, не API-схемы или модели БД. Результат хранит исходный `DependencyDeclarationDTO`, `policy="latest_stable"`, status, reason, checked_versions, excluded_versions, optional target metadata и optional `UpdateSourceRequest`. У исключения сохраняются исходная версия, стабильный код причины и yanked_reason при наличии. Не копировать в результат весь индекс файлов.

Обычные статусы — selected, no_update, skipped. Ошибки сети и бюджета — исключения, а не дополнительный псевдоуспешный статус. Данные current сохраняются ровно в переданном виде; имя запроса нормализуется. Scope, marker и ограничения остаются внутри исходной декларации. Не объединять разные декларации одного имени в единственную версию проекта.

Альтернативы: класс из одного метода и отдельный пакет нескольких сервисов отклонены как ненужные слои. Изменение парсера отклонено: статический инвентарь должен сохранять гарантию отсутствия сети.

### 2. Короткий допуск входа без сетевого уточнения current

Сначала проверить source_kind и version_state, затем наличие и PEP 440 корректность current. При неподходящем входе вернуть skipped: unsupported_source, conflicting_current, unsupported_current, unknown_current или invalid_current. В частности, конфликтующий DTO с непустой строкой current не становится допустимым. Имя пакета проверяется и нормализуется до сетевого запроса; некорректное имя — ValueError с контекстом входа.

Для registry с declared_pin/locked корректный current может быть prerelease, post или local: он сравнивается как есть, без попытки заменить публичным релизом. Его существование в PyPI на этом шаге не доказывается. Возможное отсутствие current обнаружит отдельный сбор заданной пары и вернёт свою типизированную ошибку.

Альтернатива — разрешить диапазон или запросить установленную версию из окружения. Отклонена: это другая задача и противоречит уже принятому контракту неизвестности.

### 3. Порядок PEP 440 и правило стабильности

Один раз получить `get_package(name)`, проверить нормализованное имя результата и разобрать versions с `packaging.version.Version`. Невалидные строки, в том числе ValueError из чрезмерно длинного числового компонента, записать в exclusions как invalid_version. Исключить dev, prerelease и local (коды dev_release, prerelease, local_version); post-релизы оставить. Local исключается именно как публичный target; входной current может его содержать.

Дедуплицировать по равенству Version. Представитель эквивалентных строк определяется независимо от порядка: предпочесть `str(Version)` при наличии среди исходных строк, иначе лексикографически минимальную строку группы. Имена оригинальных исключённых вариантов сохраняются для диагностики; одинаковые записи не дублируются. Затем взять только версии строго выше current и отсортировать по убыванию Version. Даты публикации и строки filename не участвуют.

При отсутствии более новых стабильных кандидатов вернуть no_update с no_newer_stable без metadata-запросов. Это также исключает downgrade с нового prerelease/local current на более старый стабильный релиз. Меньшие и равные версии не требуется записывать в exclusions: причина no_newer_stable и прочитанный индекс уже определяют исход сравнения.

Альтернатива — взять последний элемент массива, сравнить строки или довериться project metadata latest. Отклонена: провайдер не гарантирует порядок или соответствие default version нашей политике.

### 4. Проверка yanked через конкретный release endpoint

Для кандидатов по убыванию вызвать `get_package_info(name, candidate)`. Проверить имя и `Version(metadata.version) == Version(candidate)`. Ошибка значения или несоответствие дают `InvalidPyPiResponse`, не переход к следующему кандидату. Yanked=true означает исключение даже при пустом yanked_reason; первый проверенный неотозванный релиз становится target. Если все кандидаты проверены и отозваны — no_update с no_newer_stable.

Признак yanked берётся из metadata релиза. Это не требует расширения DTO или разбора wheel/sdist filenames: сейчас DTO файла не содержит version, а provider уже умеет читать нужный release endpoint. Список файлов и requires-python не используется для проверки установимости. В MVP выбирается релиз для изучения изменений, а не готовое install plan.

Альтернатива — вычислить release yanked из файлов индекса. Отклонена для этого шага из-за необходимости нового сопоставления filenames с версиями. Несколько metadata-запросов приемлемы и ограничиваются бюджетом. Выбранная metadata сохраняется в результате; повторное чтение target в `collect_sources` допускается ради сохранения существующего API. Пара запросов к PyPI не образует атомарного снимка, последующий сбор сохраняет собственные факты о релизе.

### 5. Политика не ограничивается совместимостью

Не вызывать SpecifierSet.contains, Marker.evaluate и проверку requires-python при выборе target. Это осознанное правило пользователя для MVP: например, `<2` при current=1.5 не мешает выбрать последнюю 3.0, а требование Python>=3.14 у target не заменяет его более старым релизом для Python 3.11.

Target metadata, декларация и её constraint provenance остаются доступными. В документации прямо указать: выбор кандидата ещё не оценка риска и не гарантия установки. Обработчик конкретного окружения и фильтр совместимых версий сейчас не добавляются.

### 6. Ошибки, бюджеты и отмена

Вся операция чтения PyPI, начиная с индекса, помещается в общий `asyncio.timeout(timeout)`. До каждого metadata-запроса проверить `max_release_checks`. По умолчанию это не больше 32 release checks плюс один index request за 120 секунд. Уже существующие ограничения провайдера продолжают действовать на каждый запрос.

Если лимит достигнут, но непроверенных кандидатов нет, можно вернуть no_update. Если кандидаты остаются, поднять `UpdateSelectionError` с package, reason=release_check_limit и checked_versions. Собственный общий deadline даёт тот же тип с reason=deadline_exceeded; ошибки самого PyPiProvider сохраняют исходные типы и контекст, в том числе retry_after. CancelledError проходит без преобразования. Нет retry, скрытого fallback после 404 или продолжения после ошибки metadata.

Ошибки не становятся «обновлений нет». Будущий batch caller сможет изолировать их по декларациям; текущая функция обрабатывает одну запись и не определяет поведение целого мониторинга.

## Risks / Trade-offs

- Проверки нескольких yanked релизов увеличивают число API-запросов → ограниченные последовательные проверки; бюджетная ошибка вместо недоказанного результата.
- Последняя стабильная может нарушать ограничения Python/проекта → сохранить ограничения и metadata, не присваивать статус совместимости; это намеренная политика MVP.
- Legacy и эквивалентные строки версий → Version, детерминированный tie-break и явные exclusions; регрессия на большие числовые компоненты.
- Изменение PyPI между индексом и metadata → типизированная ошибка при исчезновении/несоответствии кандидата; без тихого выбора более старой версии.
- Повторные декларации вызовут повторные обращения → принимать как ограничение первой функции; batch/cache не вводить до появления общего исполнителя.

## Migration Plan

Изменение аддитивное, миграций БД нет. Добавить модуль и тесты, зафиксировать правило в docs/mvp.md, дать примеры в docs/dependencies.md и docs/pypi.md. Пример получает инвентарь, явно обходит декларации, вызывает selector и передаёт selected.request в collect_sources. Skipped/no_update отображаются отдельно; исключения остаются видимыми вызывающему. Не делать автозапуск частью read_dependency_inventory или регистрации проекта.

Проверить пример на настоящем инвентаре с локальными pyproject/uv.lock и MockTransport PyPI, без сети и модели. Откат — прекратить вызов selector и убрать новый модуль; прежние парсер и явный сбор пары сохраняются.
