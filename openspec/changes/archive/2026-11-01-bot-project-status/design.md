# Design

## Context

Мотивация и объём описаны в `proposal.md`. Сейчас `commands.py` содержит заглушку `/status`, `RepoService` умеет только первоначально сохранять репозиторий и зависимости, а `Repo` и `RepoDependency` имеют soft delete. В БД отсутствуют проверки и оценки. `bot.py` не создаёт зависимости обработчиков. Alembic содержит шаблонный URL, `target_metadata = None`, версии миграций отсутствуют. Python-тестов нет, существующие JS-тесты проверяют логику фронтенда.

## Goals / Non-Goals

**Goals:** независимые от aiogram DTO и сервисы, согласованные снимки результатов, отдельная сессия на запрос, проверяемый путь миграции SQLite с сохранением существующих проектов.

**Non-Goals:** микросервисы, очередь задач, универсальный DI-контейнер, полноценные отчёты с участками кода, авторизация Mini App и реализация остальных команд. Доступ в этом изменении защищает `/status`; это не заявление о защите ещё не реализованных интерфейсов.

## Decisions

### 1. Прямой вызов сервиса с внедрением зависимости

Добавить `StatusService.get_overview()` в `app/services/status.py`, принимающий `AsyncSession`. Он возвращает dataclass DTO: список `ProjectStatusDTO` с `project_id`, `project_name`, `dependencies_count`, `latest_run`, `latest_snapshot_at`, `status_counts`. Последние два поля nullable совместно; заполненные счётчики всегда имеют все шесть ключей. Время в DTO — UTC. Ошибка хранилища преобразуется в прикладную `StatusUnavailable` с сохранением исходной причины.

В `bot.py` собираются зависимости; middleware маршрута `/status` сначала проверяет `ALLOWED_CHAT_IDS`, затем открывает сессию и передаёт сервис через контекст aiogram. Handler только вызывает сервис, форматирует результат и отвечает. Проверка доступа предшествует открытию сессии. Общая фабрика сессий допустима, общая `AsyncSession` — нет; контекст закрывает сессию и откатывает незавершённую транзакцию при ошибке.

Альтернативы: SQL в handler смешивает транспорт и сценарий; HTTP между ботом и сервисом усложняет один self-hosted процесс. Отдельный repository-интерфейс пока не нужен: сервис может выполнять SQLAlchemy-запросы и тестироваться на временной SQLite.

### 2. Запуски и неизменяемые снимки

Добавить `MonitoringRun`: `id`, `repo_id`, `started_at`, `finished_at`, `state`, `error`. Состояния запуска: `running/succeeded/failed`; проверка согласованности требует время завершения для terminal-состояний и причину для `failed`. Это отдельно от одноимённого статуса зависимости `failed`: ошибка анализа одной библиотеки не означает сбой всего мониторинга.

Добавить `DependencyResult`: `id`, `run_id`, `name`, `current_version`, nullable `latest_version`, `status`. Связь по запуску и копия имени/версии сохраняют историю даже после изменения или soft delete текущей зависимости. Ограничения: FK, уникальность `(run_id, name)`, допустимые значения статуса; индексы запусков по `(repo_id, started_at, id)`. Имена результатов нормализуются по правилам Python-пакетов (нижний регистр, последовательности `-`, `_`, `.` заменяются на `-`) перед проверкой уникальности.

Отдельный `MonitoringStateService` предоставляет операции начала, успешного и неудачного завершения запуска для будущего конвейера. Успех сохраняет полный переданный снимок и terminal-состояние в одной транзакции; условное обновление `running` защищает от повторного завершения. Неверный снимок или ошибка записи откатывают всю операцию. Неудача сохраняет только состояние запуска и причину, без публикации частичных результатов. История terminal-запусков не редактируется через сервис. Сохранение пустого успешного снимка разрешено. Сервис записи работает с отдельной сессией на операцию и владеет её транзакцией.

Альтернатива — хранить последний статус на текущей зависимости — теряет историю и допускает смесь результатов разных проверок. JSON со счётчиками не хранит исходные результаты и затрудняет проверку согласованности; выбираются строки снимка и вычисляемые счётчики.

### 3. Правила чтения и свежести

`latest_run` выбирается по `(started_at, id)` по убыванию. Последний успешный снимок выбирается среди `succeeded` в том же порядке: позднее завершение старого запуска не должно заменять более новый снимок. Счётчики вычисляются только для выбранного успешного запуска. Они описывают состав его снимка, тогда как `dependencies_count` описывает текущие неудалённые зависимости; после изменения состава они могут различаться и подписываются соответственно.

Читать сводку одной SQL-выборкой с подзапросами агрегатов: это даёт согласованный снимок данных и избегает N+1 и async lazy loading. Фильтровать `Repo.deleted_at IS NULL`, текущие зависимости считать с тем же условием. Сортировка — имя, затем ID. Отсутствие проектов — пустой список, отсутствие успешной проверки — `None`, успешный пустой снимок — шесть нулей. Начатый запуск без завершения остаётся `running`; восстановление зависших проверок относится к будущему конвейеру, таймауты здесь не изобретаются.

### 4. Формат ответа и настройки доступа

Добавить `ALLOWED_CHAT_IDS: list[int]` с безопасным значением по умолчанию `[]`; окружение задаёт JSON-массив, в том числе отрицательные ID групп. Каждый разрешённый чат видит общий набор проектов, ID пользователя в запрос сервиса не передаётся. Детальный просмотр и callbacks не добавляются: ранее предложенные кнопки не были подтверждены и потребовали бы отдельного сценария.

Новый чистый форматтер `/status` возвращает список текстовых сообщений. Он использует русские названия из `src/view/app/logic.js` как согласованный словарь: несовместимость, требует проверки, анализ не удался, ждёт анализа, низкий риск, актуальна. Показывает все шесть счётчиков и пояснение «Низкий риск не гарантирует совместимость». Даты явно подписываются UTC. Для ошибки или выполняющегося запуска старый снимок подписывается собственным временем и предупреждением о свежести. Для пустого состояния использовать тексты спецификации.

Отправлять plain text с явным отключением parse mode. Делить по блокам проектов, при чрезмерно длинном блоке — по строкам, затем безопасным фрагментам с учётом UTF-16 длины Telegram; предел 4096, включая разделители. Не усекать причины ошибок или проекты. Ошибку `StatusUnavailable` логировать с traceback и отвечать нейтрально; ошибки отправки Telegram не маскировать как сбой БД. Технические детали провайдеров и секреты не должны попадать в сохранённую пользовательскую причину ошибки; подробности остаются в логе.

## Risks / Trade-offs

- [В БД пока нет истории] → существующие проекты получают честное состояние без проверок, результаты не генерируются из текущих версий.
- [Снимки увеличивают БД] → история сохраняется полностью; retention остаётся отдельной задачей.
- [Сбой процесса оставляет `running`] → отображать сохранённый факт с временем начала; будущий исполнитель должен будет определить восстановление.
- [Бот пока не умеет выполнять проверки] → путь записи проверяется интеграционными тестами без искусственного наполнения рабочей БД.
- [Существующая БД может быть создана без Alembic] → использовать документированный baseline после проверки структуры и резервной копии; не stamp автоматически.
- [Документация содержит единственное число и открытый вопрос о числе проектов] → обновить относящиеся к этому решению разделы `docs/mvp.md`, `docs/dev-docs.md`, `docs/frontend.md`; не внедрять переключатель Mini App.

## Migration Plan

1. Настроить единый `DATABASE_URL` (по умолчанию существующая SQLite), используемый engine и Alembic. Alembic не должен требовать токен бота или LLM-настройки для запуска. Подключить метаданные всех моделей и FK enforcement SQLite.
2. Создать baseline-миграцию существующих таблиц `repos` и `dependencies`, затем отдельную миграцию истории проверок и результатов. Временные SQLite проверяют upgrade с нуля и добавление новой схемы поверх baseline с заполненными проектами.
3. Для существующей БД без версии: остановить приложение, сделать резервную копию, сверить схему с baseline, явно выполнить stamp baseline, затем upgrade head. При несовпадении остановиться и описать необходимость отдельного переноса, не удалять данные.
4. Добавить `ALLOWED_CHAT_IDS` в инструкцию настройки; без неё `/status` запрещён. Перезапустить приложение после миграций.
5. Откат: остановить приложение, вернуть предыдущую версию. Downgrade новой миграции удаляет только новую историю, оставляя проекты и зависимости; перед ним сохраняется резервная копия. Откат baseline на рабочей БД не выполнять.
