# Spec Delta

## Purpose

Собирать через PyPI материалы двух явно заданных версий Python-пакета для последующего анализа обновления, сохраняя происхождение, различия метаданных и ограничения доступных источников.

## ADDED Requirements

### Requirement: Сбор заданной пары релизов
Система MUST принимать имя пакета, текущую и целевую версии и получать метаданные именно этих релизов через PyPI. Результат MUST отдельно содержать запрошенные версии и идентичность возвращённых релизов. Система MUST NOT заменять недоступную версию последней доступной или выбирать обновление самостоятельно.

#### Scenario: Оба релиза доступны
- **WHEN** запрошены текущая `1.0` и целевая `2.0` версии пакета
- **THEN** результат содержит метаданные обоих конкретных релизов в соответствующих ролях и исходные запрошенные версии

#### Scenario: Варианты имени пакета
- **WHEN** передано имя `Example.Pkg`, которое PyPI разрешает как `example-pkg`
- **THEN** запросы используют принятую провайдером нормализацию и оба релиза относятся к одному пакету

### Requirement: Сохранение описаний и происхождения
Система MUST сохранять описания обеих версий без изменения текста вместе с content type, идентичностью релиза, ролью current/target и указанием PyPI как источника метаданных. Пустое или отсутствующее описание MUST явно обозначаться как недоступное. Описание MUST NOT автоматически считаться release notes.

#### Scenario: Одинаковые описания
- **WHEN** обе версии содержат один и тот же README
- **THEN** оба описания доступны с отдельным происхождением и их совпадение не трактуется как отсутствие изменений библиотеки

#### Scenario: Описание отсутствует
- **WHEN** описание равно null, пустой строке или состоит только из пробельных символов
- **THEN** результат сохраняет исходное значение и отмечает отсутствие содержательного описания этой версии

### Requirement: Опубликованные ссылки на источники
Система MUST сохранять все project URLs и homepage обеих версий с исходными значениями, названиями и происхождением. Ссылки MUST классифицироваться по явному названию как changelog, release_notes, source, documentation, homepage или other. Неизвестная ссылка MUST NOT угадываться по домену или пути. Классификация MUST NOT означать проверку содержимого или официальности ресурса.

#### Scenario: Известные и неизвестные названия
- **WHEN** метаданные содержат `Changelog`, `Release Notes`, `Source`, `Documentation` и неизвестный `Community`
- **THEN** результат сохраняет все записи, первые четыре получают соответствующие категории, а `Community` получает `other`

#### Scenario: Различающиеся источники версий
- **WHEN** текущая и целевая версии публикуют разные URL changelog
- **THEN** результат сохраняет обе ссылки с происхождением, не заменяя одну другой

#### Scenario: Совпадающие ссылки
- **WHEN** обе версии публикуют одинаковую ссылку
- **THEN** её принадлежность каждой версии сохраняется, даже если представление результата объединяет совпадения

### Requirement: Доступность ссылок на изменения
Система MUST отдельно сообщать наличие подходящих ссылок категории changelog или release_notes для каждой версии и для пары в целом. Подходящей считается абсолютная HTTP(S)-ссылка без credentials с непустым хостом. Неподходящие значения MUST сохраняться с причиной исключения. Содержимое ссылок и их доступность по сети MUST NOT проверяться этим модулем.

#### Scenario: Есть только исходники и документация
- **WHEN** опубликованы Source и Documentation без явно обозначенного changelog или release notes
- **THEN** сбор завершается успешно, но результат сообщает отсутствие подходящих ссылок на изменения

#### Scenario: Неподходящий URL
- **WHEN** Changelog содержит относительный адрес, неверный URL, credentials или схему вне HTTP(S)
- **THEN** исходная запись сохраняется с причиной исключения и не считается подходящей ссылкой на изменения

### Requirement: Различия требований релизов
Система MUST сохранять исходные requires_python, requires_dist и dynamic обеих версий. Различие requires_python MUST определяться по исходным значениям; добавленные и удалённые requires_dist MUST определяться по точному составу строк без учёта порядка и повторов. Различия MUST NOT интерпретироваться как доказательство несовместимости или как разрешённый набор зависимостей окружения.

#### Scenario: Изменены требования
- **WHEN** requires_python меняется с `>=3.10` на `>=3.11`, а `lib>=1` заменяется на `lib>=2`
- **THEN** результат содержит оба ограничения Python, удалённую строку `lib>=1` и добавленную `lib>=2` без оценки совместимости

#### Scenario: Изменён только порядок
- **WHEN** requires_dist обеих версий содержит одинаковые строки в разном порядке или с повторами
- **THEN** добавленные и удалённые требования отсутствуют, а исходные метаданные сохранены

#### Scenario: Динамические требования
- **WHEN** dynamic любого релиза содержит `requires_dist`
- **THEN** результат явно отмечает ограниченность опубликованных требований и не объявляет их полным составом зависимостей

### Requirement: Отозванный целевой релиз
Система MUST сохранять yanked и yanked_reason целевого релиза без фильтрации и автоматического выбора замены. Отзыв MUST передаваться как факт о релизе, отдельно от совместимости проекта.

#### Scenario: Отзыв без причины
- **WHEN** PyPI сообщает, что целевой релиз отозван, с пустой или отсутствующей причиной
- **THEN** результат сохраняет признак отзыва и исходную причину, не формируя заключение о совместимости

### Requirement: Ошибки не подменяются отсутствием материалов
Система MUST завершать сбор ошибкой, если метаданные любой версии не получены. Ошибка MUST сохранять тип и контекст PyPI, включая пакет, версию и доступные сведения о rate limit. Частичные данные MUST NOT возвращаться как успешный результат; отмена MUST передаваться вызывающему без преобразования.

#### Scenario: Целевой релиз отсутствует
- **WHEN** текущая версия получена, а запрос целевой версии завершается ошибкой not found
- **THEN** вызывающий получает ошибку целевой версии вместо успешного результата с пустыми источниками

#### Scenario: Лимит или временный сбой
- **WHEN** запрос любой версии завершается rate limit, timeout или ошибкой сервера
- **THEN** ошибка передаётся с доступным контекстом без автоматического повтора и без вывода «changelog отсутствует»

### Requirement: Сбор отдельно от анализа
Система MUST выполнять только чтение метаданных запрошенных релизов PyPI и формирование результата в памяти. Система MUST NOT загружать опубликованные страницы или файлы, вызывать LLM, исследовать код проекта, выполнять тесты, изменять БД или присваивать статус совместимости. Успешный сбор MUST NOT означать, что изменения библиотеки проанализированы.

#### Scenario: Завершён только сбор
- **WHEN** метаданные двух версий успешно получены
- **THEN** вызывающему доступны материалы и ограничения без дополнительных обращений к опубликованным URL, запуска анализа или изменения состояния мониторинга
