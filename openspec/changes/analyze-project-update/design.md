# Design

## Context

Мотивация и границы описаны в `proposal.md`. Компоненты уже имеют самостоятельные контракты: `RepoService.open_source` владеет временным GitHub-снимком, инвентарь читает его синхронно, селектор возвращает запрос пары версий, а `collect_sources`, `fetch_sources` и `analyze_sources` выполняют отдельные этапы. `fetch_sources` закрывает переданный загрузчик; PyPI-клиентом владеет вызывающий код.

`agent/comparer/context.py` предоставляет `collect_context` с внедрёнными model и toolkit. Он создаёт compare-агента с инструментами и структурированным `ContextResult`. Полный `comparer/graph.py` остаётся каркасом для следующих этапов и здесь не используется. Индекс создаётся синхронно через `get_repo_index`; нужны только чтение и поиск по Python-коду.

`cfg/settings.py` создаёт глобальные настройки вместе с обязательным BOT_TOKEN. Его нельзя импортировать из ручного запуска. Скрипт `artifacts/run-analysis.py` использует собственный HTTP wrapper с `ainvoke`, но он не реализует tool calling для comparer. В зависимостях проекта сейчас нет отдельного адаптера chat-модели OpenAI-compatible API. Полезные локальные tracing/rendering helpers находятся в игнорируемом `artifacts/` и не могут быть зависимостью поставляемого кода.

## Goals / Non-Goals

**Goals:**

- Добавить тонкий вызывающий слой с внедряемыми клиентами и моделями; сохранить существующие операции пригодными для самостоятельного использования.
- Дать пользователю проверяемую цепочку «декларация → current/target → изменение с цитатой → потенциальное использование в SHA», доступную после удаления снимка.
- Сохранять промежуточные результаты при отказах и позволять проверять весь сценарий без сети, ключей и платных вызовов.

**Non-Goals:**

- Реализовывать незавершённые узлы полного графа или переопределять контракты селектора, парсеров и извлечения.
- Создавать универсальный pipeline engine, реестр этапов или отдельный service-класс на одну функцию. Используются обычные функции, конкретные DTO и небольшие модули по ответственности.
- Объявлять найденные места доказанными регрессиями. Структурная проверка ссылки и точное совпадение цитаты не проверяют семантику вывода.

## Decisions

### 1. Отдельный ручной entry point и явное владение ресурсами

Добавить `python -m lovogit.cli.analyze_update --repo URL --package NAME [--source auto|pyproject|requirements] [--langfuse]`. CLI разбирает аргументы, создаёт каталог запуска и зависимости, вызывает async-функцию оркестрации и печатает итог с путями. Основная логика располагается в `app/project_update/`: orchestration, DTO и сохранение отчёта; код модели группируется в `app/providers/llm/`, настройки — в `cfg/`. Допустим небольшой модуль tracing рядом с ручным запуском, без общего фреймворка наблюдаемости.

Бот и `main.py` не участвуют. Альтернатива запуска полного comparer graph отвергнута: она добавляет неготовые узлы генерации тестов и sandbox и меняет смысл MVP.

Внешний контекст владеет GitHub/PyPI и модельными HTTP-клиентами, внутренний — снимком; индекс существует только внутри снимка. Вызов `fetch_sources` учитывает его текущую ответственность за закрытие loader. Разбор инвентаря и построение индекса выносятся из event loop. При отмене фоновой работы освобождение снимка дожидается её завершения: простая отмена `to_thread` не останавливает поток. Индекс закрывается доступным API underlying Repository; если его API не даёт явного close, рабочее владение изолируется и документируется без выдуманного метода.

### 2. Одна запись инвентаря, без нового разрешителя

Уточнение владения индексом, согласованное при реализации: SQLite в `code_symbol_index` привязан к потоку создания. Для одного индекса используется отдельный executor с одним worker; построение, все обращения поисковых инструментов и закрытие `Repository.storage.connection` выполняются только там. Существующие схемы инструментов сохраняются, их async-вызовы направляются в этот executor. При отмене вызывающий дожидается уже начатой операции до закрытия соединения и удаления снимка. `Repository.clean()` не используется, поскольку он также удаляет файлы в корне проекта.

Сначала получить снимок и инвентарь с выбранным источником. `failed` инвентарь останавливает анализ как failed; `no_sources` даёт skipped. `partial` сохраняется как ограничение, но допускает работу с найденной однозначной записью. По canonical name должно остаться ровно одно совпадение. Ноль даёт dependency_not_found, несколько — ambiguous_dependency с scopes, markers, версиями и происхождением. Даже одинаковая версия в нескольких записях не делает их одной записью.

Далее вызвать существующий `select_latest_stable_update`. Не добавлять ручные current/target overrides или выбор платформы. Альтернатива выбора первой декларации нарушает сохранённую неоднозначность инвентаря. Если это ограничение помешает реальным прогонам, адресный выбор декларации станет отдельным расширением.

### 3. Последовательный pipeline с сохранением исходных результатов

Порядок: snapshot → inventory → selection → collection → fetching → extraction → index → compare. Индекс строится лениво, только если есть принятые изменения для исследования. Клиент PyPI переиспользуется; сбор по-прежнему сам получает metadata заданной пары. Отсутствие подходящих ссылок не обходится подстановкой GitHub release text или угадыванием URL.

DTO запуска содержит версию формата, run ID, параметры и время, сведения о репозитории/SHA, исходные DTO этапов, результаты по изменениям и общий статус. Этапы имеют outcome, reason и ограничения; не начавшиеся этапы получают not_run с причиной. Сохранять данные после завершённых этапов, затем финализировать отчёт в `finally`; ошибка сохранения не должна скрывать первоначальную ошибку.

Правила итогового статуса:

| Ситуация | Статус |
| --- | --- |
| Нет декларации, неоднозначность, no_sources, пропуск селектора | skipped |
| Селектор подтвердил отсутствие более нового target | no_update |
| Обязательный этап не выполнен из-за ошибки без пригодного результата соответствующего анализа | failed |
| Остались необработанные данные, неполный инвентарь, ошибки отдельных документов/поисков либо ограниченный поиск | partial |
| Предусмотренные операции завершены без таких пропусков | completed |

При отсутствии материалов после выбранного target — partial с no_materials. Ошибки всех extraction-вызовов дают failed; успех части сохраняется как partial. Успешное извлечение нуля изменений допускает completed, если нет других пропусков, с явным предупреждением о неизвестном влиянии и покрытии. Обычная неопределённость полноты истории сохраняется всегда и сама по себе не превращает каждый completed в partial. Ошибка экспорта Langfuse хранится отдельно от статуса анализа.

CLI завершает completed/no_update/skipped кодом 0, partial — 2, failed — 1, прерывание — 130; отдельный сбой запрошенного экспорта делает код ненулевым, сохраняя исход анализа в JSON. Ошибки аргументов и невозможность создать каталог показываются непосредственно в CLI.

### 4. Реальный адаптер модели с tool calling

Добавить `langchain-openai` и создавать `ChatOpenAI` с настроенными base URL, key, model, timeout, ограничением output tokens и `max_retries=0`. Не фиксировать версию библиотеки в плане: разрешённая версия попадёт в lock при реализации. Поддержать только `LLM_PROVIDER=openai_compat`; другие значения отклонять понятной ошибкой при достижении LLM-этапа. Это соответствует текущему пользовательскому Polza-каналу; Google GenAI потребовал бы отдельной интеграции и тестов.

Извлечение использует MODEL_CHEAP без инструментов, compare — MODEL_STRONG с существующими поисковыми инструментами и структурированным ответом. При совпадении model IDs допустимо переиспользовать конфигурацию. Непустой LLM_REASONING_EFFORT передаётся явно, пустой не отправляется: текущий Polza model ID уже задаёт режим reasoning. Настройки LLM загружаются лениво без глобального `_Settings`. Callback-трассировка должна охватывать и прямой `ainvoke` extractor, и вложенные генерации/tool calls агента.

Альтернатива расширения локального HTTP wrapper потребовала бы собственной реализации протокола инструментов, structured output и callback API. Официальный адаптер уменьшает объём такого кода; тесты с подменённым transport/model проверяют запросы без платных вызовов.

### 5. Поиск по принятым изменениям с сохранением происхождения

Присвоить каждому принятому изменению ID в пределах запуска. Отдельно сохранить unscoped и rejected, не запускать по ним compare. Для каждого принятого изменения построить `DependencyChange`: package/current/target, `changed_api` как символ либо пустая строка, `change_description` как категория и описание. Связь с полным DTO и evidence остаётся в оркестраторе и не зависит от того, повторила ли её модель.

Переиспользовать `collect_context` и `Toolkit` для одного изменения за вызов, последовательно. `analysis_complete` относится только к полноте поиска. Ошибки отдельных вызовов сохранять, продолжать в пределах общего бюджета. Ссылки usages и related_tests проверить относительно корня, убедиться в существовании файла и строки, сохранить небольшой snippet и GitHub permalink на SHA. Невалидные ссылки оставить как непроверенные с диагностикой; не читать пути вне корня и не включать их как проверенное evidence.

Альтернатива одного вызова на все изменения затрудняет связь результата с источниками, частичное сохранение и ограничение бюджета. Отдельного analyze/solution этапа здесь нет.

### 6. Артефакты принадлежат запуску

Каталог по умолчанию — `artifacts/runs/<UTC timestamp>-<canonical-package>-<random suffix>/` относительно корня текущего checkout; случайный суффикс и исключительное создание предотвращают перезапись. Ни package, ни repo URL не используются как произвольный путь. Поддержку отдельного output-root в MVP не добавлять.

Сохранять `report.json`, `report.html`, `trace.json`, `langfuse-otel.json` и при отправке `langfuse-export.json`. Большие исходные тексты и записи model/tool допускается хранить отдельными JSON/text файлами с относительными ссылками из report.json; HTML содержит необходимые тексты самостоятельно и работает без временного снимка, JS и CDN. Сохранение JSON выполнять атомарной заменой файла внутри каталога запуска.

Промотировать полезную логику локальных helpers из `artifacts/` в отслеживаемый пакет и покрыть контрактами; не импортировать игнорируемые файлы. HTML экранирует все модельные и внешние данные, цитаты выделяет по проверенным диапазонам. Для сырых ответов показывать, какие записи приняты, отклонены или остались unscoped, с привязкой к ID проверенных изменений. Поскольку формат сырого JSON может содержать escapes, не искать цитату в нём простым строковым совпадением: точные offsets принадлежат тексту источника.

### 7. Конечные бюджеты с явной диагностикой

Существующие лимиты fetch/extraction/selection сохраняются. Новые defaults: общий deadline запуска 600 секунд, не больше 10 compare-вызовов, до 12 обращений к модели и 24 выполнений поисковых инструментов на изменение, timeout compare 60 секунд, до 5 000 output tokens на генерацию. Ограничение числа вызовов обеспечивается счётчиком до отправки запроса; graph recursion limit — дополнительная защита, а не замена счётчику. Значения задаются отдельными настройками ручного запуска.

Для фрагмента кода — до 20 строк и 8 000 символов, для сериализованного результата инструмента — до 30 000 символов, для сохраняемых model/tool данных — общий бюджет 20 MiB. При превышении не выдавать усечённые данные за полные: сохранять признак, исходную длину, доступную часть и причину; не начинать новые генерации после исчерпания общего бюджета. Материалы источников уже ограничены upstream настройками. Принятые изменения сохраняются все в пределах upstream бюджета, независимо от лимита compare.

Общий deadline прекращает новые этапы и активные async-запросы; обязательное освобождение ресурсов и ожидание уже запущенной синхронной работы могут занять дополнительное время. Внешняя отмена передаётся после best-effort сохранения, экспорт при отмене не запускается.

### 8. Локальные трейсы всегда, Langfuse по флагу

Run ID и trace ID связывают стадии, поколения модели и инструменты. Использовать callbacks для model/tool событий и явные span для обычных этапов; родительские связи хранить по контексту выполнения, без общего небезопасного стека на весь процесс. Сохранять сообщения, tool args/results, model ID, timestamps, finish reason, usage и ошибки. Ключи и auth headers исключать из сериализации по построению, а не сохранять целиком объекты settings или HTTP requests.

Повторно использовать OTLP JSON-представление существующего tracing helper, не вводя обязательный Langfuse SDK. `--langfuse` валидирует отдельные настройки и отправляет уже сохранённый payload после финализации. Команда `python -m lovogit.cli.export_trace RUN_DIR` отправляет его без модели и других клиентов. Receipt фиксирует trace ID, hash payload и accepted/partial/failed/unknown; accepted, partial и неопределённый исход не пересылаются автоматически, чтобы не дублировать принятые spans. Явный отказ до принятия допускает повтор. Экспорт имеет timeout и не повторяется автоматически.

Доступный usage сохраняется как есть и в нормализованных token counters; данные Polza о стоимости в RUB остаются metadata с валютой. Не вычислять USD и не выдумывать стоимость при отсутствии данных провайдера.

## Risks / Trade-offs

- Совпавшая цитата может сопровождать ошибочную привязку версии или неверную интерпретацию → отчёт сохраняет сырые ответы и limitations, не называет такие выводы доказанной регрессией; улучшение семантической валидации остаётся отдельной работой.
- У пакета может не быть явно опубликованных ссылок changelog/release notes → partial с причиной, без обхода ограничений готового загрузчика.
- Модель или канал могут не поддержать обязательный tool calling → явная ошибка compare с сохранённым extraction, без скрытой замены модели.
- Индекс и агенты могут пропустить динамические импорты, wrappers и непрямые использования → отчёт сообщает ограниченность Python-поиска и не делает выводов о совместимости.
- Сырые сообщения содержат прочитанные фрагменты проекта → сохраняются в игнорируемом каталоге; отправка этих данных в Langfuse выполняется только явно. Credentials экземпляра не включаются в артефакты.
- Большие ответы или прерывание могут оставить неполный трейс → сохранять checkpoints и признаки усечения; не считать отсутствие span успешным завершением этапа.

## Migration Plan

Схема БД и существующие команды не меняются. Добавить пакетные модули, адаптер модели и lock, затем документацию запуска и независимых настроек. Старые игнорируемые прогоны остаются доступными; новый формат помечается собственной версией, чтение старых файлов не обещается. Откат — удаление нового entry point и зависимости, без миграции данных. Автоматические проверки используют fake transport/model и временные каталоги; платный smoke run не является обязательным условием реализации.
