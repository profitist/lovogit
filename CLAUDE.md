# LovoGit

Агент, который следит за обновлениями зависимостей проекта и объясняет, что новая версия значит для конкретного кода: что изменилось, какие места в проекте это задевает, насколько рискованно обновляться.

Статус: проектирование. В репозитории только заготовка Python-пакета (`uv`, Python 3.14, `src/lovogit/`).

## Документация

- [docs/mvp.md](docs/mvp.md) — проблема, решение, аудитория, состав MVP и критерий успеха.
- [docs/dev-docs.md](docs/dev-docs.md) — конвейер обработки, возможности, формат отчёта, принципы, нерешённые технические вопросы.
- [docs/backlog.md](docs/backlog.md) — что отложено после MVP.
- [docs/frontend.md](docs/frontend.md) — минимальный веб-интерфейс: реестр зависимостей и критичность обновлений.

Перед работой над задачей сверяйся с `docs/mvp.md`: если задача не входит в MVP, её место в `docs/backlog.md`. Если задача упирается в пункт из раздела «Не решено» в `docs/dev-docs.md` — сначала спроси, не выбирай молча.

## MVP в двух строках

Только Python-проекты. Найти реальное обновление → найти затронутый код → прислать в Telegram обоснованное уведомление. Без SaaS, без сложного веб-интерфейса (только экраны просмотра из `docs/frontend.md`), без автоматической правки кода.

## Правила, которые нельзя нарушать

1. **Факт отдельно от предположения.** Каждый вывод отчёта опирается на источник (changelog, release notes, документацию) или на найденный участок кода. Догадка помечается как догадка.
2. **«Не нашли» не значит «совместимо».** Отчёт явно говорит, что проверялось, а что нет.
3. **У каждого уведомления есть ссылки на официальные источники.**
4. **Уведомление должно помогать принять решение.** «Вышла новая версия» без анализа — не уведомление.
5. **Решение об обновлении принимает разработчик.** LovoGit не меняет зависимости и код проекта.
6. **Сначала узко и качественно**, потом шире: новые языки, интеграции и автоматизация — только после того, как работает анализ для Python.
